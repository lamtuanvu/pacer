# App web UI decision — 2026-10-15

Status: owner decision recorded 2026-10-15. Supersedes
[core-contract decision 7](../specs/2026-10-14-core-contract-design.md#decisions-2026-10-14)'s
choice of a native desktop app with no web UI.

## Decision

The owner chose a web UI served by the pacer daemon on 2026-10-15.
`pacer serve` serves the embedded app at `/app/` on loopback.
`pacer open` opens it in a browser. The first delivery is a placeholder;
the full app follows. It uses the same v2 operations as other clients.

A desktop wrapper can come later using the same bundle, without a second
frontend codebase. See the [app spec](../specs/2026-10-15-pacer-app-design.md)
for the screens, API operations and delivery order.

## Security model

- Loopback only. Every route, including `/health`, checks Host against
  `127.0.0.1` or `localhost` and the server's actual port.
- `pacer open` creates a single-use code that expires after 60 seconds.
  Exchanging it creates an HttpOnly, SameSite=Strict cookie session with a
  sliding 30-day expiry. Codes and sessions are stored as SHA-256 hashes in
  files with mode 0600 under `PACER_HOME/app/`, a directory with mode 0700.
  Secret comparisons use constant-time checks. `pacer open --logout` clears
  all browser sessions.
- Cookie auth applies only to `/app/*` and `/v2/*`. Requests other than
  GET/HEAD require a matching loopback Origin and `X-Pacer-Client: app`.
  When present, `Sec-Fetch-Site` must be `same-origin` or `none`.
- Bearer auth remains available for existing clients. There is no CORS;
  OPTIONS requests receive 405. App pages use a restrictive Content Security
  Policy, nosniff and no-referrer headers. Index and auth pages disable caching.
- The app receives no API keys, account emails or tokens in API results,
  events or logs. Agent configuration changes require explicit consent in
  the core API.
