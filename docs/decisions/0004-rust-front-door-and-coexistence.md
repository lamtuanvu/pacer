# Rust front door and cross-runtime coexistence

Status: proposed 2026-10-22; governance adoption and M1 exit evidence pending.

## Context

The Rust migration moves the installed entry point and public transports before porting the domain core. Clients must retain one versioned service API while Rust and the existing TypeScript implementation coexist. The public native endpoint also has older desktop/update-helper clients that authenticate the service using kernel process identity; replacing the socket owner with the core child would break that contract.

This decision refines the [Rust migration design](../specs/2026-10-20-rust-host-migration-design.md). It preserves [clients over one local service](2026-10-16-clients-over-local-service.md), [plugin host and Rust strangler](2026-10-19-plugin-host-and-rust-strangler.md), the [SQLite task store](2026-10-19-sqlite-task-store.md) including retention, and [desktop OTA](0001-desktop-ota.md).

## Decisions

1. The installed `pacer` is the Rust front door from M1. Native startup paths include version reporting and the status line. Commands not yet native execute the sibling `pacer-core`, compiled with Bun. `pacer serve` supervises the internal core with generation-specific credentials and restart backoff. `pacer api --stdio` owns the external stdio transport and forwards operations still implemented by the core. Moving an operation requires parity evidence; clients never choose an internal runtime.
2. Rust owns public HTTP/SSE/WebSocket transport and authentication. Private core HTTP uses its own loopback ephemeral listener and internal credential. Public request/result/error and stream semantics remain compatible. Native trust is compiled into supported signed app builds; ambient environment, caller-supplied PID/path/role or unsigned code cannot grant it.
3. In a supported signed macOS paired app, Root creates and retains the public native Unix listener. After verifying the exact owned signed core child and sealed app/sibling layout, Root transfers a listener duplicate using SCM_RIGHTS over a private Unix socketpair. The core verifies its actual signed parent and the sealed pairing before receiving and adopting the listener. Received descriptors are validated and marked close-on-exec before task execution. Root alone owns pathname/owner-record cleanup, checked against recorded directory and entry identities; child close only closes its duplicate and accepted channels.
4. The inherited listener preserves the old helper's view of Root as the kernel service peer and preserves the original connecting desktop/helper audit identity observed by the accepting core. No application-supplied forwarded audit token replaces kernel identity, and public native frames/ABI remain compatible. Logical service registration/readiness/journals use Root; helper bootstrap authenticates its actual Root parent; the core independently verifies that returned helper incarnation and Root-parent relationship. A private fixed control request asks Root to shut itself down; it does not authorize signaling an arbitrary PID. Socketpair EOF retains orphan shutdown behavior. Actual old-helper signed live proof remains required.
5. Root directly spawns immutable update helpers for its authenticated core generation. A dedicated anonymous helper-control channel is transferred with fixed marker `C` after listener marker `P`; it is private to the signed paired processes. Root accepts bounded strict requests only for the fixed private helper layout, verifies original manifest/journal helper binding where applicable, checks the fixed helper signer role and exact static/dynamic CDHash, and invokes only `--ota-pipe` with a cleared environment. Root constructs the existing helper bootstrap; the core verifies actual helper parent == Root. Paired mode has no fallback to core-parented spawning and never substitutes a new helper into an old authorized transaction. Existing core transaction eligibility and helper authorization remain mandatory; this narrow spawn capability does not grant an operation itself.
6. Handing helper streams to the core may convey durable recovery authority. Before handoff, failures terminate and reap the unhanded child. After any possibly successful handoff, control EOF, core-generation retirement or Root shutdown does not automatically kill the helper: authorized recovery must survive pipe loss. Explicit abort retains SIGTERM to the exact owned unreaped child, followed by wait, with no automatic escalation. One Root-wide limit of four live helpers spans core generations; handed reapers retain their slots until actual process exit. The bounded channel has read/spawn deadlines, while synchronous bounded filesystem/signature validation cannot be preempted by the asynchronous timer.
7. Original launch argv remains exact. Literal `--port 0` records ephemeral bind intent; the separately observed actual nonzero public port scopes internal propagation and native listener identity. Other mismatched port values are refused. Managed registration verification independently requires the exact registered argv, actual port and Root incarnation. Launch intent is not a substitute for those checks.
8. Releases install and update `pacer` and `pacer-core` as a verified pair. Paired app metadata requires both sealed executable siblings, with the same supported version and CLI signer role. Standalone CLI self-repair may recover its own-version verified companion under its existing policy. Executables inside a macOS app are never repaired piecemeal: an incomplete or mismatched bundle requires a complete verified app replacement. Linux packages retain the unmodified compiled Bun companion alongside Rust; release validation must exercise the real packages.
9. Both runtimes use one PACER_HOME and its established durable formats. Shared file writers use the existing exclusive operation locks, atomic replacement and restrictive modes. Task state uses the existing single SQLite database with its schema, immediate transactions, WAL/busy-timeout behavior, JSON write-through/import recovery and retention compatibility. The file-only sketch in the migration design does not replace the SQLite ADR. Authenticated private IPC may carry transient coordination and capabilities; clients continue through the public API.
10. Governance adoption does not certify M1 completion or authorize publication. Required checks, artifact-level parity, conformance, signing/package validation and CT-11 live reports must identify the actual source/artifacts under review. Missing surfaces stay UNVERIFIED. The maintainer owns adoption and release decisions.

## Consequences

Two sibling executables ship during M1/M2. The core remains a supervised implementation detail, and private IPC is part of the coexistence implementation. Packaging must preserve both code identities and the outer app seal. Native listener transfer avoids weakening older helper authentication but requires signed artifact tests in addition to transport unit probes. SQLite and retained JSON compatibility remain unchanged by the language migration.
