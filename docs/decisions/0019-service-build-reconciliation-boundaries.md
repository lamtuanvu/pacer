# Service build reconciliation boundaries

Status: proposed, 2026-11-03. This decision enables no capability. Maintainer adoption is pending. It records the conditional direction in the approved [design](../specs/2026-11-03-service-build-reconciliation-design.md); it does not amend established rules or establish native guarantees.

## Context and capability matrix

The desktop and service can report the same release version while running different front-door or core builds. A version or a self-reported digest is not proof of the running pair. P1/P2/P4/P5/P6 and ARCH-1–3/9, API-1–5 and SEC-1/3–5/7/8 remain in force. Each machine has its own authority. A candidate is never automatically installed or downgraded; equal-version divergence is blocked without a separately approved authenticated monotonic ordering policy.

| Source / platform | Current finding | Reconciliation capability |
| --- | --- | --- |
| Managed macOS launchd, either architecture | Existing admission participates in a shared SQLite transaction, but full writer coverage, transferable fencing, native identity and recovery are not proven for this transaction. | Blocked until every proof below and signed native validation on both architectures passes. |
| Exact-allowlisted legacy macOS standalone | Allowlist is identification, not exclusion. All four shipped 0.6.2/0.7.1 entries declare `admissionExclusion: false`; direct self-update bypasses reservation. | Blocked, including these official artifacts. A future exact artifact needs a separately audited exclusion baseline and all other proofs. |
| Homebrew, npm, unknown or external ownership | No source-specific exclusion and effect/recovery contract established here. | Guidance only; owner manages external services. |
| Linux or other unproven platform | Native proof and recovery contract not established. | Guidance only. |

Even a higher version is only a candidate after protocol, state, provenance and platform compatibility checks. Claims, missing fields, an unavailable service or a reported zero work count are not proof. Both measured components must be bound to a canonical external manifest in the signed destination, and the running job, process incarnation and actual code must be independently bound to that pair. Same-path file measurement alone cannot establish running bytes; PID reuse and replacement require reinspection at each effect boundary. Unsupported OS measurements block capability.

## Proposed ownership and admission

Core owns idle decisions, durable state and journals. Desktop is a client, with a separately bundled trusted shell for inspection, explicit consent and status; service HTML cannot confer authority. The public API remains additive and authenticated, with write Origin/client checks and no caller-selected paths, hashes, commands, keys or trust flags. A bounded private authenticated coordinator/recovery interface returns only transaction receipt, public phase and bounded reason, including after service loss. It exposes no journal, database, grant or private authority; desktop never opens internal service state. Failure to authenticate or reach it yields unknown/recovery-needed, not success. The prior independent design rereview identified this P1/ARCH-1 ambiguity; this boundary resolves it as a proposal, not an existing interface.

Today `withDesktopCoordinator` uses a short synchronous SQLite `BEGIN IMMEDIATE` with FULL synchronous journaling on a private stable database. Participating lease creation and reservation mutation serialize across processes on the same database; the physical transaction is released before entity locks or native I/O. External blocker observation precedes the reservation transaction, and nonparticipating writers are not fenced. The schema stores a reservation ID, with no owner epoch or transfer CAS. It is not proof of cross-process transfer or a reboot fence.

A future reconciliation reservation must atomically check enrolled durable leases and a revision, record a distinct transaction kind, boot binding, owner and monotonically changing epoch, and transfer by compare-and-swap to an authenticated surviving coordinator. Only the acknowledged owner at the current epoch can effect or release. Stale owners, unknown kinds/epochs and ambiguous transfer fail closed; durable evidence is retained and admission remains closed where enforceable. Acquire logical admission before entity locks; release the short SQLite transaction before entity locks, awaits and native I/O. Existing entity-locked lease validation must not invert this ordering. This is a required contract, not an assertion that the current code implements it. Filesystem/SQLite durability, lock behavior after crash and reboot, external writer exclusion and recovery closure must be demonstrated on each supported OS and filesystem; unknowns block capability.

## Proposed effects, authentication and recovery

The pinned bundled coordinator survives source shutdown. A separate legacy bootstrap coordinator uses a fresh inherited authenticated channel; the legacy process is never treated as a signed coordinator. The helper independently authenticates the coordinator and signed bundle over a private channel, verifying a one-use, kind-scoped grant bound to transaction, source job and incarnation, installation, destination, helper, boot, nonce and allowed effects. Peer identity, channel provenance, grant replay resistance and signed helper validation are required platform evidence, not assumed OS guarantees. Native inspection must prove user, job, boot, process birth and actual running component pair, then recheck identities and fence before effects.

After explicit consent and reservation, persist the exact original registration including disabled override and arm independent signed recovery before stopping the exact inspected job. Record intent before each effect and observation after it. Register and start only the verified bundled destination; commit only after job/process/pair binding, authenticated readiness and compatible state read. On uncertainty retain evidence and recovery-needed status; never blindly repeat, overwrite the source or restore user-data snapshots. Reboot invalidates forward consent. Recovery may only complete recorded cleanup after commit or undo recorded effects and prove exact original registration, code and readiness; missing proof remains blocked. No elevation or generic shell is authorized.

## Existing transactions and migration

OTA, adoption and reclaim retain their existing versioned records, grants, behavior and distinct reclaim interruption warning (ADRs 0001 and 0011). Reconciliation needs a distinct versioned discriminator and scope; unknown kinds and versions fail closed and cannot be parsed as another transaction. Admission must prevent overlap with these operations, including attached-service paths, before any effect; current shared reservations alone do not prove all such exclusion. Migration must preserve old record interpretation and reject ambiguous in-flight records rather than rewriting or borrowing their authority. Verify cross-format non-overlap, crash boundaries and recovery before advertising capability.

## Consequences and evidence gates

No implementation, platform or source is certified by this ADR. Writer inventory and unresolved coverage are recorded in `.work/reviews/reconciliation-task1.md`. Future delivery requires isolated multi-process race and fault-injection tests, authenticated status and protocol checks, signed macOS validation on both architectures, source-specific proof, current-revision CT-11 live evidence, applicable UI evidence and independent final review. Remote live testing requires separate maintainer approval. Any missing proof remains UNVERIFIED and blocks capability. OD-2 ADR naming remains open; this numbered file follows the current AGENTS.md instruction without resolving the policy conflict.
