# Plugin protocol v1.5.0

Generated by `bun run plugin:protocol`. Check freshness with `bun scripts/plugin-protocol-doc.ts --check`. The JSON Schema for every message is in [plugin-protocol.schema.json](plugin-protocol.schema.json).

## Overview

A plugin is a subprocess the host starts lazily. Both sides speak newline-delimited JSON-RPC 2.0 on the plugin's stdin and stdout (one object per line, 1 MiB cap). stderr is captured to `$PACER_HOME/logs/plugins/<id>.log`. Both sides send requests, so each side matches replies by id. Additive changes do not bump the version; removals bump the major, and the host serves the previous major for one pacer minor release.

The host sends `plugin.hello` first and refuses a plugin whose reply has a different protocol major, or an id or version that differs from its manifest. Every call carries a deadline owned by the host; on expiry it sends the notification `$/cancel` with `{ id }`, fails the call with `plugin_timeout` and drops any later reply.

Protocol 1.1 adds optional top-level `_meta: { capabilityCall }` correlation on host extension requests and their capability calls. Legacy peers may omit metadata; uncorrelated calls never gain new account-scoped authority. Tokens are bounded opaque call identifiers and expire with their owning request.

Protocol 1.5 adds policy/task/event contracts and mutually negotiated `policyObservations` for the host and TypeScript SDK. Task reads require declared and granted `tasks.read` plus a current owning call or process-generation read owner. The exclusive `_meta: { readOwner }` arm permits only task reads and subscription management; mixed, foreign or retired owners never fall back to unowned/effect capability handling. Existing peers/capabilityCall correlation remain supported; peers without this feature cannot use the observation methods. Rust SDK observation helpers are not implemented: the standalone policy protocol crate supplies contracts, not SDK runtime support.

The staged `executor` point currently defines only `contributes.executor.backends: ["direct"]` and `executor.available`. Availability receives a credential-free strategy name and has a 10 s host deadline. This contract has fake conformance coverage but no production caller; run, stop, resume, session state, task patching and executor effects require a separately reviewed owner-bound contract.

The staged `hostRunner` point names only fixed SSH script IDs and uses bounded arguments, results and finite deadlines. The `hosts` capability defines `open`, `run` and `close` with host-owned broker sessions. Callers supply only a configured alias and fixed script input; the host derives the SSH target and selects the provider. Production forwarding and the SSH adapter cutover remain separate, and byte streaming and transfer ownership require a later reviewed patch.

Peers explicitly negotiate `chunkedResults` in hello features. For a large usage result, the plugin sends sequential `$/resultChunk` requests containing the original numeric request id, contiguous byte offset and at most 256 KiB of base64 JSON bytes, with the original call metadata. It waits for each `{ bytes }` acknowledgement, then replies to the original request with `{ _chunkedResult: { bytes } }`. The host resolves only after exact-length complete JSON assembly under the original authority/deadline. Legacy peers keep ordinary replies; chunks never renew authority.

SDKs: `@pacer/plugin` (TypeScript) and `pacer-plugin` (Rust).

## Lifecycle

States: `disabled`, `refused`, `needs_grant`, `idle`, `starting`, `ready`, `failing`. Bundled plugins are enabled unless listed in `plugins.disabled`; installed plugins need a recorded grant covering their capability set and drop back to `needs_grant` when a new version asks for more. A crash restarts the plugin after 1 s, doubling to 30 s; three crashes within a minute mark it `failing` until `plugin.enable` or a service restart. Calls to one plugin run one at a time unless the manifest sets `reentrant`. Service stop sends SIGTERM, then SIGKILL after 2 s.

## Errors

| Code | Meaning |
|---|---|
| `plugin_timeout` | A call passed its deadline. |
| `plugin_unavailable` | The plugin is disabled, refused, needs a grant, is failing, or exited mid-call. |
| `plugin_refused` | Manifest or handshake rejected. |
| `capability_denied` | Capability not declared, not granted, or outside its scope. |
| `unknown_plugin` | No plugin with that id. |

Plugin replies use JSON-RPC errors `{ code: -32000, message, data: { code, hint? } }`; a `data.code` the host knows is passed through, anything else becomes `plugin_unavailable`.

## Policy observation notification contract

`$/event` is a host → plugin notification: no request id and no reply. Its payload is a canonical v3 API event. Initial subscription requires a current host-owned `diagnostic.ping` (doctor) or `policy.before` call, declared/granted `events.subscribe`, and negotiated `policyObservations`; a pending usage or other call cannot bootstrap it. The TypeScript SDK automatically subscribes for `onEvent` before replying to the first such call unless its handler already subscribed. Metadata-only enable does not start the process or subscribe.

A subscription starts at the current cursor and delivers only future requested event types, plus every reset. It runs independently of public API subscribers. One opaque read owner is retained per process generation after the initial call settles; it carries no file, command, HTTP, secret or install resources. Disable, removal, manifest/config/grant changes, stdout EOF and process exit revoke it. Executor work grants cannot subscribe to global events; task reads retain their original work-grant scope and expiry.

The TypeScript callback receives an isolated tasks/events/log/config client, never the transient effect client from an overlapping call. Task reads use the public task projections (list defaults to 100, maximum 500, states filtered before limit) and the existing complete-frame size limit. Log/config keep their existing declaration and grant checks.

Reset means discard incremental assumptions and re-read the snapshot. Host delivery and TypeScript callback backlogs are bounded to 128 notifications and 256 KiB including active delivery; overflow discards obsolete queued notifications for a bounded reset. Persistent blocked delivery/reset retires the process or SDK lifecycle rather than growing the queue. Callback exceptions are contained with a safe diagnostic. EOF or retirement aborts pending callback reads; recovery requires a fresh valid process generation and subscription.
