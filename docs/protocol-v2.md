# Client protocol v2

Generated by `bun run protocol:doc`. Check freshness with `bun scripts/protocol-doc.ts --check`.

This compatibility API is served for one pacer minor release alongside [protocol 3.0](protocol.md). New integrations should use v3.

## Overview

The protocol version is `2.8.0` (semver). Clients can use HTTP + SSE from `pacer serve`, or line-delimited JSON-RPC 2.0 over stdio from `pacer api --stdio` without a daemon. Both transports call the same operation registry.

HTTP binds to `127.0.0.1` only, and every request must carry `Host: 127.0.0.1:<port>` or `localhost:<port>` (otherwise 421). Every `/v2/*` route requires `Authorization: Bearer <token>` (the server token file has permissions `0600`) or, for the pacer app in a browser, the `pacer_session` cookie from `pacer open` (session exchange requires bearer authentication). Cookie requests other than GET/HEAD also need a loopback `Origin` and `X-Pacer-Client: app`; a `Sec-Fetch-Site` other than `same-origin` or `none` is refused. There is no CORS: `OPTIONS` returns 405. Operation request bodies are capped at 256 KiB in UTF-8 bytes; larger bodies return `413 too_large`. Operations and session exchange use POST; the other routes below use GET.

Additive fields do not bump the protocol version. Clients must ignore unknown fields and event types. Removing or renaming fields requires a major version bump; the previous major is served for one pacer minor release.

Operation inputs are validated. No operation runs free text in a shell. `task.delegate`, `task.retry` and `task.answer` refuse calls when the API process itself is an executor session. Under proposed API-5 amendment 0.13.0, an executor can request `dispatch.child` with a service-issued task/attempt grant. That grant authorizes only scoped work operations and descendant reads; it never authorizes global operations or self-review. Executor sessions without a valid grant remain unable to delegate.

## Errors

HTTP route errors after authentication use `{ "error": { "code": "...", "message": "...", "hint": "..." } }`; `hint` is optional.

| Code | HTTP status |
|---|---|
| `invalid_input` | 400 |
| `not_allowed` | 403 |
| `unknown_task` | 404 |
| `unknown_executor` | 404 |
| `unknown_op` | 404 |
| `conflict` | 409 |
| `too_large` | 413 |
| `internal` | 500 |
| `plugin_timeout` | 504 |
| `plugin_unavailable` | 503 |
| `plugin_refused` | 422 |
| `capability_denied` | 403 |
| `unknown_plugin` | 404 |

Missing or invalid HTTP tokens return 401 with the plain-text body `unauthorized`. A wrong HTTP verb returns 405 with `invalid_input`.

JSON-RPC errors use `{ jsonrpc: "2.0", id, error: { code, message, data? } }`:

| Failure | JSON-RPC code | Data |
|---|---|---|
| Invalid JSON | -32700 | Omitted; response id is null |
| Invalid request envelope | -32600 | Omitted; response id is null |
| Unknown method | -32601 | `{ code: "unknown_op", hint? }` |
| Invalid params | -32602 | `{ code: "invalid_input", hint? }` |
| Other core or internal error | -32000 | `{ code, hint? }` |

## HTTP routes

| Route | Response |
|---|---|
| `POST /v2/session/exchange` | Bearer authentication only; creates an app cookie session, returns 204 with Set-Cookie and Cache-Control: no-store |
| `GET /v2/hello` | `{ protocol, pacer, ops, events }`: protocol and pacer versions, operation names and event types |
| `GET /v2/snapshot` | `{ protocol, seq, snapshot }`: current snapshot and its sequence number |
| `GET /v2/events?since=<seq>` | SSE events after `since` (default 0); `Last-Event-ID` overrides the query parameter |
| `POST /v2/ops/<name>` | JSON params body; success is `200 { result }`, errors use the table above |
| `GET /v2/tasks/<id>/log?follow=1` | SSE `log` events with `{ stdout, stderr }`, starting at byte offset 0; ends with `done` and `{}` after completion |

Event cursors must be non-negative safe integers. Read a task's diff through `task.diff` using the operation route.

## Live sessions

`GET /v2/tasks/<id>/session?from=<outputOffset>` upgrades to a WebSocket on the same server. Host and bearer/cookie authorization match other versioned routes. Cookie upgrades additionally require an exact loopback Origin and reject cross-site Sec-Fetch-Site, including on GET. Browser WebSockets do not need X-Pacer-Client. A missing session returns 409; a non-upgrade request returns 426.

Binary WebSocket messages contain complete session wire frames (u8 type, u32 big-endian length, bytes), preserving output/input bytes. Text messages contain JSON control frames with a named type and body fields, for example `{type: "hello", v: 1, client: "app", label: "browser", cols: 120, rows: 40, from: 0}`. The bridge forces hello.client to app for text and binary hellos; from may be supplied in hello or the URL (URL wins). Other frame bodies are relayed unchanged. Reconnect using the last outputOffset: retained bytes resume directly, otherwise the host sends a snapshot.

Each session accepts 16 viewers. A 17th receives exit with a clear refusal. Each viewer has a 1 MiB output queue; overflow drops pending output and sends resync then a fresh snapshot. Phase 2 is read-only: take/release receive a refusal and input/size do not affect the PTY. Server shutdown closes WebSocket viewers without stopping the host.

Task events include session `{host: "builtin" | "orca" | "none", live, controller, viewers}`; session changes are throttled to once per second. terminalPresent remains for one minor release and equals session.host === orca && session.live. terminal.open accepts a preset or argv template containing {cmd}; templates never run through a shell.

## JSON-RPC methods

Send one JSON object per line. Requests use `{ jsonrpc: "2.0", id, method, params? }`; success replies use `{ jsonrpc: "2.0", id, result }`. Requests run concurrently, so clients must match replies by id. Valid notifications (requests without an id) receive no reply.

| Method | Params | Result |
|---|---|---|
| `hello` | `{ protocol: 2 }` or `{ protocol: 3 }`; default 2 during overlap | Same hello object as the selected HTTP major; call before snapshot, subscribe or operations |
| `snapshot` | None | Same snapshot object as HTTP |
| `subscribe` | `{ since?: number }`, default 0, a non-negative safe integer | `{ subscribed: true, last }`, then `event` notifications |
| Any operation name below | Its params schema | The operation result directly |

Subscription notifications use `{ jsonrpc: "2.0", method: "event", params: { seq, at, type, data } }`. A new subscription replaces the previous cursor. When input ends, event polling stops and pending requests finish.

## Snapshot

The snapshot preserves `v`, `seq`, `at`, `budget`, `mode`, `tasks`, `alerts`, `console`, `consoles`, `strategies` and `serviceInstalled`. Protocols 2.1 and 2.2 add:

| Field | Contents |
|---|---|
| `service` | Pacer version, protocol, process id and service start time; `starting: true` while the service is still computing its first status after a restart (planner, accounts and executors fill in by event); `waiting: { kind, path, since }` while a repository file-system call has been outstanding for at least a second, e.g. behind a macOS removable-volume permission prompt. `kind` is `volume` with the volume root (`/Volumes/<name>`) as `path`, or `folder` with the path itself; `since` is Unix seconds. It is absent once the call returns |
| `planner` | Planner runner and agent, used/pace percentages, delta, verdict, active hours left, reset, window, stale flag, mode and advice; null without a planner |
| `machine` | Shared local parallel-task capacity `{ used, max, hardCap, unlimited }` across all local executors. `hardCap` is the fixed cap, or null with `unlimited: true` when none is set. `max` is deprecated and stays a number for older clients: the cap when set, otherwise the sum of the enabled local executors' own limits; read `hardCap` and `unlimited` instead and never display `max`. Added fields describe the guard that holds new local starts: `memoryPressure` (`normal`, `warning`, `critical`, or null when unavailable), `memoryPressureLimit` (`critical`, `warning`, `off`), `loadPerCore` (1-minute load average per CPU core, or null), `loadLimit` (null when off), `open`, and while closed `reason` (`machine_memory_pressure` or `machine_load`) and `detail`. `detail` also reports an unavailable memory-pressure signal while the guard stays open |
| `executors` | Planner first, then default routing order: identity, account, host, model, rank, state, tone, usage, slots `{used,max}` (configured executor limit), optional limitedBy (`machine` or `host`) when a shared cap is lower, recent failures and next flag |
| `accounts` | Name, agent, source, usage, window, reset, verdict, sign-in state and executor ids; no credentials or emails |
| `counts` | Review, running, queued, ready executors, total executors, required setup items open, hosts with problems, attention items, problems (problem or blocked severity), and review/running/attention counts by repo key |
| `attention` | Service-owned Needs you items in display order; an empty array means no attention is needed |
| `today` | Local midnight `since`, settled task count, accepted, rejected, failed (including limit) and settled counts by repo key |
| `hosts` | Alias, SSH target, paused/down/checking/needs_setup/ready state, running count, max tasks, executor ids and mapped repo count |
| `repos` | Known repositories ordered by last use: `{ key, label, path }`, with canonical host/owner/repo or local hash key and main-checkout path |
| `policy` | Metadata-only `{mode: open | closed, plugins: number}`: configured failure mode and enabled policy plugin count, including enabled failing policies. No plugin starts or policy calls. Missing older-service metadata is unknown, never implied open or closed. Terminal labels use `policy: open` / `policy: closed (n plugins)`; width-constrained labels use `policy:open/n`, `policy:closed/n`, or `policy:unknown` (n is the enabled plugin count). |
| `setup` | Complete flag, count of required items open, items with id, title, status and required flag, and the same `policy` metadata as the snapshot. `setup.check` also includes policy metadata. Closed mode with zero plugins is displayed explicitly. |

Executor, account and planner rows add optional `eligibility`: `{ state, reasons, evaluatedAt, validUntil, evidenceAgeS, availability, budget, spendingRisk }`. `state` is `eligible`, `uncertain` or `ineligible`; reasons contain stable `code` and `evidenceIds`. Missing fields on older services mean unknown eligibility. Timestamps are Unix seconds; a null deadline or age means unavailable, not fresh evidence. These fields do not change the protocol major.
`routing.route` includes eligibility on ranked and excluded candidates, an `uncertain` subset and `fallback: "uncertain"` on automatic fallback candidates. Eligible choices precede uncertain ones within global and project routing. Attempts preserve the launch decision and fallback in `routing`. Preflight refreshes supported sources and checks evidence/configuration again before dispatch. Pacing verdicts and legacy state enums are not execution permission. Credits alone do not permit paid execution; `spendingRisk: "unknown"` does not mean no paid usage.
Tasks add `rev`, `repo`, `kind`, `host` and optional `source`. The snapshot includes queued and running tasks plus undismissed settled tasks updated in the last 24 hours, newest first, capped at 200. Parallel tasks use runners.<id>.max_tasks (default 1 locally or the host max_tasks remotely), with an optional shared execution.local_max_tasks cap (default `unlimited`, no fixed cap). New local tasks also wait while macOS memory pressure reaches execution.local_memory_pressure_limit (default `critical`) or the load per core exceeds execution.local_load_limit (default `off`); running tasks are never stopped. Tasks wait with queue { reason, since, position, limit?, capacity?, detail?, machine? }; no_slot waits add limit (`executor`, `machine` or `host`) and capacity `{used,max}` at the last scheduling check. machine_memory_pressure and machine_load waits add limit `machine`, a plain-words detail and machine `{ memoryPressure?, memoryPressureLimit?, loadPerCore?, loadLimit? }` with the observed values; waiting tasks are re-checked about every 5 seconds. Paused waits omit these capacity fields. Executor rows include enabled, disabled/checking/failing states and lastCheck. The snapshot includes pause from the current delegation pause; planner.modeHeldUntil is present while a mode hold is active.

Repository identity and existence reads use an in-memory cache. New paths can initially use their absolute unresolved identity until an async probe completes. Registry probes refresh at most once a minute; timeouts retain the last known value, and only confirmed missing repos without active or recent tasks are hidden. Task resolution uses bounded async filesystem and git reads, so stalled volumes do not block snapshots or event replay.

## Attention and actions

Each attention item is `{ id, kind, severity, repo, taskId?, executor?, host?, account?, title, detail, raisedAt, since, actions, notify, snoozedUntil? }`. Times are Unix seconds. Kinds are `question`, `review`, `failed`, `limit`, `stuck`, `account_signin`, `executor_down`, `host_down`, `planner_quota`, `setup` and `update`. Severity is `blocked`, `problem` or `decide`; items are ordered in that order, oldest `since` first within a severity. Clients preserve this order and use service counts rather than deriving conditions locally. Older services without `attention` may use client heuristics.

An action is `{ label, op, params, style?, confirm? }`; style is `primary` or `danger`. Show the supplied confirmation before dispatching a confirmed action. Registered operations go through the normal operation transport. `ui.open` is client navigation, never a registered service operation: `{ op: "ui.open", params: { view: "review" | "task" | "session" | "settings", id?, section? } }`.

`attention.dismiss { id }` returns `{ dismissed: true }` and also dismisses a task item. `attention.snooze { id, for: "1h" | "4h" | "1d" }` returns `{ until }`. An unknown attention id returns `unknown_task`. Dismissals last until the underlying condition clears; snoozed items are hidden until the deadline. Planner-sourced tasks enter review 600 seconds after settling; other tasks enter immediately.

A `question:<task>` item has blocked severity, important notifications, the question verbatim (first 200 characters) as detail, and Answer (`task.answer { id }`) then Stop (`task.stop { id }`) actions. The client collects the answer text before dispatching Answer.

## Activity

`activity.list { before?, limit?, repo?, kinds?, taskId? }` returns `{ entries, next }`, newest first; pass `next` as `before` for the next page. Default limit is 50, maximum 500. Each entry is `{ id, at, kind, level, text, repo?, taskId?, executor?, host?, machineId? }`, where repo is a RepoRef key, machineId is the recording machine's id once it has one (a stable device identifier), level is `info`, `warn` or `error`, and kind is `task_started`, `task_settled`, `verdict`, `retry`, `mode`, `budget_refreshed`, `executor_state`, `host_state`, `account_state`, `config` or `update`. The service retains 30 days or 20 000 entries, whichever is smaller, and records budget refreshes at most once per 15 minutes per account. Activity entries are also published as `activity` entity events. Items, actions and activity contain no credentials or emails.

## Task and repository operations

Default task lists and snapshots omit archived history. The protocol 3 task.prune and task.restore operations manage archives.
`task.get` returns full task detail: brief, attempts with logs, routing explanation, cost, acceptance timing and summary, timestamps, diffstat files, retryOptions and timeline. `task.retry_options { id }` lists alternate executors in routing order with state and reason. `task.diff { id, path? }` returns files, patch, base and worktree; `diff` remains an alias for patch in 2.x. Patches are capped at 1 MiB, or 4 MiB with a path. Running remote tasks return an empty patch and a note until changes reach the local review worktree.

`task.review` accepts verdict `accept`, `reject`, `send_back` (requires note), or `retry` (requires executor), and returns `{ task, retry? }`. Legacy `accepted: true/false` maps to accept/reject. Send back creates a retry on the same executor with the note as review feedback. Queued or running tasks cannot be reviewed.

`task.request_review` adds a human handoff note (1–2000 trimmed characters) to an unresolved done or partial task. It accepts optional `expect_rev`, returns `{ task }`, and never records an acceptance. Repeating the same note is a no-op after revision validation. Task reads/events expose additive `reviewRequest` and `acceptanceState` fields. Ordinary completion without a verdict does not generate review attention.
Task mutations `task.stop`, `task.retry`, `task.answer`, `task.review` and `task.dismiss` accept optional `expect_rev`. A revision mismatch returns `conflict` with `data.task` containing the current task; omitting expect_rev preserves unconditional behavior. Task revisions increase on persisted changes.

`task.delegate` accepts optional `request_id` (1–128 characters, deduplicated for 600 seconds), `base` (branch/ref or 7–40 hex SHA) and `source` (`planner`, `ui`, `cli`). A repo may be an absolute path or RepoRef key. HTTP client labels starting with app, desktop, orca, tui or tray default source to ui; others default to planner. `routing.route { kind?, goal?, repo? }` classifies goal when kind is absent.

`task.list { limit?, before?, repo?, states?, executor?, since? }` returns `{ tasks, next }` when any new filter/cursor parameter is supplied. Calls with only limit or no parameters retain the legacy summary array for the 2.x overlap. RepoRef optionally carries `unreachable: true` when a folder probe fails or times out; cached task repo identities are retained and a later successful probe clears the flag. `repo.list` returns RepoRefs with branches (current first, at most 50); `repo.add { path }` registers a git repository and returns its RepoRef; `repo.remove { key }` returns `{ removed: true }`.

Executor questions settle tasks as `needs_input` (label: Needs your answer). `task.ask { id, text }` records one 1–1000 character question from an executor session identified by PACER_TASK_ID. `task.answer { id, text, expect_rev? }` accepts 1–2000 characters and returns `{ task, retry }`; it creates a retry on the same executor and records answer/answeredAt on the original question. Any task not awaiting an unanswered question returns conflict, including repeat answers after the retry settles. Concurrent answers create one retry. The stored brief accumulates `qa: [{ q, a }]`, rendered after Constraints as `## Question / Answer` with verbatim Q: and A: lines. Question and answer text never goes through a shell. Executor sessions cannot answer onward. On an interactive lane (`task.delegate` with `interactive: true`) whose backend kept its worker live after the question, the answer is typed into that worker instead of a new one, and only while the worker is unsettled and its terminal still reports the lane's agent (on Orca, `terminal show`'s `agentIdentity` for the same terminal incarnation); otherwise the old worker is stopped and the retry starts fresh. The agent is launched with `exec` in place of the terminal's shell, so when it exits the terminal ends and no shell is left to read typed text. `task.send { id, text, force?, expect_rev? }` delivers 1–4000 characters to the same live agent of a running lane under the same check (conflict while the lane waits on its question; unavailable when the task has no live worker, its backend cannot deliver input or the terminal does not report the lane's agent) and records a 60-second driving lease for the caller: a service client instance (`X-Pacer-Client-Instance`, so two app windows or two MCP servers contend even under one label; only its X-Pacer-Client label when it sends none), the CLI by its terminal. `driving.by` is caller-asserted and carries that label, instance id or the CLI's OS user and terminal session id. Another caller within the lease gets conflict unless force. Task records may carry `interactive`, `group`, `driving { by, at }` and `live { backend, worker, terminal, executor, agent, since }`; a live worker holds its executor slot until it is answered, stopped, settled or idle for four hours.

## Events

The advertised v2 event types are `budget`, `task`, `mode`, `alert`, `config`, `pause`, `reset`, `executor`, `account`, `host`, `repo`, `counts`, `attention`, `activity`, `job` and `notify`. A `config` event `{ area, at }` follows every successful configuration change (`area` is one of `config`, `accounts`, `runners`, `routing`, `strategy`, `hosts`, `setup`, `update`, `plugins`); clients refetch that area. Events have `{ seq, at, type, data }`; `seq` is the resume cursor, `at` is the publication time (legacy entries fall back to read time), and `data` carries the event payload.

The additive `pause` event carries `{ until, reason, by }` (PauseState, with a Unix-seconds deadline and nullable fields) after `delegation.pause`. `delegation.resume` and timed pause expiry publish `{ removed: true }`; expiry is published once. Clients update their pause state directly.

Entity events carry the whole row or `{ id, removed: true }`. Counts and per-task progress changes are coalesced to at most one per second. Clients must ignore unknown fields and event types.

HTTP SSE frames carry the sequence number as `id`, the type as `event`, and the JSON payload as `data`:

```text
id: <seq>
event: <type>
data: <JSON payload>

```

Frames end with a blank line. Streams poll every second by default and send a `: keepalive` comment every 15 seconds. JSON-RPC subscriptions poll every 500 ms by default.

The outbox retains the last 1000 entries. If a positive resume cursor predates the retained entries, a single `reset` event precedes the retained events. Its sequence is one less than the oldest retained entry, and its data is `{ reason: "events were dropped; fetch the snapshot again" }`. Fetch `/v2/snapshot` (or call `snapshot`) again and resume from its sequence to recover the full state.

## Scheduling and mode holds

`delegation.pause { for, reason? }` pauses new work for whole minutes, hours or days, up to seven days; `delegation.resume {}` resumes it. Queued tasks drain from the pump, runner exits and API reads. `mode.hold { mode, until? }` holds the chosen mode until the supplied timestamp, the planner window reset, or seven days when unknown. `mode.release {}` releases it. Planner quota attention offers Keep normal and clears while held.

## Jobs and terminal targets

Long operations share a job per (kind, target): host.check, runner.check, host.repo.setup, host.clean and update.apply. In the daemon they return immediately; without it the operation waits for completion. job.get, job.list and job.cancel expose progress. Jobs contain id, kind, target, state, steps, startedAt, endedAt and optional error; states are running/passed/failed/cancelled. Completed jobs expire after 24 hours. Every state or step change publishes a job entity event to API clients, without channel notifications. Orphaned running jobs fail on service recovery.

Sign-in, strategy builds and host terminals use fixed commands. Automatic terminal selection tries Orca, the configured terminal.open preset (falling back to legacy terminal.app on macOS), tmux, then returns a copyable command with opened:false. Explicit targets are orca, terminal and tmux. Account signedIn:false reflects an authentication failure and clears after a successful fresh usage read. runner.check tests the CLI, sign-in, usage and a scratch task without using a user repository.

## Remote hosts

host.get returns checks, facts, ExecutorRow objects, recent completions, mapped repositories, account folders and worktree information. host.set changes max_tasks or paused. Host state precedence is paused, down (two consecutive reachability failures), checking, needs_setup (failed checks or unmapped known repositories), ready. The pump probes hosts with enabled executors every 300 seconds; the first success clears host_down. Running tasks keep their state. host_down offers Run checks and Pause host, while new work can route elsewhere. host.repo.setup requires consent:true; host.clean supports dry_run; host.terminal opens SSH. Disabled executors still prevent removing their host.

## Clients

Clients register with `client.register { kind, version, notifier? }` (kinds `app`, `desktop`, `orca`, `tui`, `status`, `tray`, `cli`) and renew with `client.heartbeat { client_id }` every 30 seconds; a lease lapses after 45 seconds. `client.list` returns live clients and the snapshot's `service.notifier` names the active notifier. The service decides what to notify from attention items and the notification level (`off`, `important`, `all`) and delivers each `notify` event once per attention occurrence to the most recently registered live notifier. With no notifier it posts a system notification itself (osascript on macOS, notify-send on Linux) without actions.

`/state` and `/console/*` were removed in 2.6. The bearer-only `/link` and legacy `/events` routes are removed in 3.0 (404); use the versioned snapshot and events routes. The Orca storage bridge, channel sends, command lines and `pacer console` are retired. `task.retry_all { ids }` retries several tasks and reports the ones it skipped.

`X-Pacer-Client: <kind>/<version>` labels delegated tasks; it is never authentication. Valid labels match `/^[a-z][a-z0-9:-]{0,31}\/[0-9A-Za-z.+-]{1,32}$/`; invalid labels are ignored. The existing `X-Pacer-Client: app` cookie-write check is unchanged. `X-Pacer-Client-Instance: <id>` (1–64 letters, digits, `.`, `_`, `:` or `-`) names one running client, such as an app window; it only identifies a `task.send` driving-lease holder and is never authentication.

TypeScript clients in this repository use `ApiClient` from `src/api/client.ts`. `connectClient` picks HTTP when `pacer serve` answers `/health` with `X-Pacer: 1`, and otherwise runs in-process. `PACER_API=inprocess` forces in-process.

The Orca plugin worker reads the v2 API over HTTP when `pacer serve` is running, otherwise through a `pacer api --stdio` child; it registers as a notifier and delivers targeted service notifications. If no API is available, the panel shows “Update the pacer plugin” with `pacer update`. Use `pacer open` or the TUI for actions.

HTTP `subscribe` reconnects with `Last-Event-ID` to resume from the last seen event.
