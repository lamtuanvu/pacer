# Desktop service build reconciliation

Status: proposed design, 2026-11-03. The user selected the direction below; this written design is awaiting approval. It does not authorize implementation or change an ADR. Durable architecture changes require an ADR under ARCH-9 before implementation is delivered. Existing established rules and ADRs prevail over this proposal.

## Intent and scope

The desktop should explain when its bundled CLI and the local running service do not come from the intended build, including when their release versions are equal. For an independently verified, compatible service that participates in the necessary admission and recovery contracts, offer an explicit, idle-only change to the bundled service. Preserve work and user data. For an external, unknown, unsupported or unverifiable service, explain the blocker and its appropriate management path; never infer permission to take it over from a mismatch or an idle count.

This is local, per-installation reconciliation, not an app update, remote deployment, general service installer, automatic downgrade, or busy-work handover. Existing complete-app OTA and the separately proposed consented reclaim remain separate transactions. In particular, reclaim under [ADR 0011](../decisions/0011-desktop-service-takeover-reclaim.md), where applicable, requires its own explicit interruption warning; it is not the idle guarantee proposed here. Desktop update with running work remains outside scope ([running-work decision](../decisions/2026-10-29-service-upgrade-with-running-work.md), [part C design](2026-10-29-desktop-update-with-running-work-design.md)).

## Approaches and tradeoffs

1. **Detection and guidance only:** lowest risk and works with old peers, but leaves eligible users to repair mismatches manually.
2. **Detection plus a durable, idle-only service transaction:** the selected direction. Reuse adoption, admission, native verification and rollback only where their actual source, destination and recovery contracts hold; extend them as needed under a distinct transaction kind. This repairs compatible services without silently stopping work, but requires a participating baseline and native validation.
3. **Handover while busy:** potentially reduces waiting but requires a separate trust and compatibility contract for surviving runners and session hosts. Existing CLI handover does not establish desktop safety, so defer it.

This design proposes details within the selected direction; the user has not approved this document or its outstanding product decisions.

## Identity, compatibility and trust

A version is a compatibility/display attribute, not identity. Each component embeds a schema-versioned descriptor containing its release version, build identifier, component role, target OS and architecture; it does **not** contain its own final digest or the final digest of a component that embeds it. After building the front door and core independently, the release process measures their final bytes and binds those digests and descriptors together in a canonical external manifest. The signed desktop bundle binds that manifest and its bundled CLI/core and helper; desktop identity uses the platform's signed-code bundle measurement, not a digest embedded in the bytes it measures. The release process must define canonical encoding and verify the complete manifest-to-bundle binding before shipping. No circular self-hash is required.

The service's additive authenticated capability reports its embedded descriptors and claimed front-door/core relationship, not a self-attested measurement. Native inspection must bind the actual running front-door executable and actual core process or loaded executable to their measured code identities and to the manifest pair, including independently built pairs; a currently named file alone is insufficient. Where the OS cannot prove the running bytes and relationship, report unverified and refuse mutation. Same version with any different measured component is a mismatch; absent, malformed or unrecognized identity is **unknown**, never match. A root match with a different core is mismatch. Reproducible builds share identity only when measured components match. Dirty, local and non-reproducible builds are measured from actual outputs; unsigned development manifests are diagnostic only and confer no production trust. Architecture differences are distinct identities.
Descriptors and public build IDs are claims and diagnostics, not credentials. The native boundary independently verifies the signed destination, publisher and manifest, current user, boot and process incarnation, registered job, actual running executable and core identity, and the relationship between those observations and the descriptor. A file at the same path, PID alone, port, health response, public registration kind, or signature alone cannot prove the running component pair. If the platform cannot establish that binding, status is unverified and mutation is refused. Pin identities and recheck them at each effect boundary, including after any process or registration change; reject drift and PID reuse. Do not execute an unknown source merely to identify it.

Compatibility is evaluated independently of equality: protocol major and supported compatibility window, state/schema read and write compatibility, architecture, source/destination provenance, admission coverage of all launch and maintenance entry points, native inspection, authorization, outcome verification and recovery capabilities must all be established. Compare trusted release versions for direction: a destination with a lower release version is a downgrade and is blocked. Equal release versions with different measurements are divergent, not ordered by their build IDs; by default they are blocked unless an independently authenticated, monotonic release ordering and an explicitly approved policy establish a forward transition and compatible state. Missing, ambiguous or non-monotonic ordering is unknown and blocked. A higher release version is only a candidate, never proof of compatibility. No version equality or public build ID authorizes a downgrade; any future downgrade requires a separately approved policy. Unsupported or ambiguous values fail closed. Legacy official sources are eligible only under the reviewed exact-artifact allowlist and audited admission baseline of the [legacy bootstrap design](2026-10-22-desktop-legacy-service-bootstrap-design.md); existing unsupported releases are not made eligible by this design. Native adoption is not advertised until its signed native validation is complete.

## Assessment and interface

The service owns work admission and the API (P1); a narrowly scoped core coordinator survives the source process and the signed native helper enforces OS identity and effects as described below. The desktop is a thin client, except for its bounded trusted native presentation and verification boundary. An additive authenticated read exposes bounded identity, capability, transaction status and reason codes. Old clients ignore unknown fields; new clients treat absent fields or unsupported protocol as unknown/unavailable. Any new operations and errors follow P4 and API-1–5, with generated protocol documentation and mappings. Requests carry an opaque inspected candidate, revision and idempotency key, never caller-chosen paths, hashes, commands, keys or trust flags. Native inspection and helper authentication are not replaced by the API. Preserve loopback authentication, Origin and client checks, no CORS, secret handling and no elevation (P5/P6, SEC-1/3–5/7/8).

Assessment distinguishes: matching verified components; known mismatch with verified compatible managed source; verified source requiring supported adoption; unknown build; external ownership; unverified provenance or process; incompatible/newer build; missing admission/recovery capability; and unavailable platform. A matching claim without native proof is still unverified. An attached external service stays attached, and its own installer or package manager controls changes. Present a specific reason and safe next step, rather than a generic restart button. Do not expose private authority or credentials in responses, logs or diagnostics.

### Trusted fallback and authority

The signed desktop supplies a local bundled shell page (or native equivalent) independently of the service origin, following [ADR 0011](../decisions/0011-desktop-service-takeover-reclaim.md). It remains available on connection timeout, refusal, missing old API, unsupported protocol, unverified or hostile service page, and after source stop or reconnect. The shell displays native inspection and authenticated coordinator/journal status with provenance and unknown values marked; it never treats service-supplied HTML or a web response as native evidence. It may invoke only the bounded inspection, status, consent and cancellation operations below through the authenticated native bridge. Inspection and presentation confer no permission to stop a job or decide idle. If the bundled shell or trusted inspection cannot be established, show unavailable and refuse mutation.

A verified compatible service UI may request that the native shell open this flow; its request is not consent. An unverified service page cannot invoke or impersonate the confirmation; the user opens the trusted shell from desktop-owned chrome. Consent is obtained only there, binds the inspected candidate and revision, and cannot supply paths or trust flags. A disconnected/old service can receive guidance, but no change action unless all eligibility and admission proofs are independently established. The native shell reads durable transaction status after a reconnect or process loss and shows recovery-needed even when no service responds. Preserve ADR 0007's ability to continue current work and ADR 0011's separate reclaim flow and interruption warning; neither mismatch nor fallback implies reclaim authority.

### Surviving coordinator and bounded authority

For a managed source, the authenticated service admits and records a waiting intent under its existing service contract. Before any stop, it hands a one-use, transaction-scoped authorization and the durable reservation to a pinned bundled core coordinator, started by the signed desktop over an authenticated private channel. For an eligible legacy source, use the distinct pinned bundled CLI bootstrap coordinator specified in the [legacy bootstrap design](2026-10-22-desktop-legacy-service-bootstrap-design.md#core-bootstrap-coordinator): the desktop starts it over a fresh inherited channel; it verifies the desktop peer, bundle, home, port and one-use session. It is not the legacy service, does not schedule work or bind its port, and uses a narrowly scoped source capability for the exact audited artifact and admission baseline. The helper authenticates this coordinator, never the legacy process as a signed coordinator. The coordinator and helper must be verified as belonging to the pinned signed bundle before use; existing code is not proof this new handoff exists.

In both paths, the durable shared admission gate, rather than a service-held in-memory lock, excludes all audited launch and maintenance writers. Under that gate, atomically record transaction ID, owner epoch and reservation state, then transfer control to the authenticated coordinator with an acknowledged compare-and-swap; the old service cannot release or reacquire it for this transaction. The helper verifies the same durable reservation and a non-replayable grant bound to transaction kind, source job and process incarnation, destination and helper identities, installation, boot, nonce and allowed effects. No generic adoption or OTA grant is broadened. Transfer, crash fencing and exclusion across reboot require a reviewed implementation of the actual shared SQLite/lock contracts; if atomic continuity or any writer coverage cannot be proved, do not advertise the capability. A stopped or restarted source cannot mint, replay or extend the grant; changed process, session or boot invalidates any not-yet-started authorization.

The coordinator persists phase and receipt, arms the independent signed recovery job and invokes the helper for only the recorded stop, registration and start effects. It survives source exit; if it or the desktop dies after effects start, recovery reads the journal and fenced reservation, proves its own authority and resumes or restores only recorded effects. A reboot invalidates forward consent; recovery may undo recorded effects, not initiate a fresh switch. Failure before acknowledged transfer leaves the source and gate unchanged or safely releases the reservation; an ambiguous transfer, lost fence, helper authentication failure or uncertain effect retains evidence and closes admission where enforceable, with recovery-needed status. Cancellation is honored only before durable reservation/preparation; afterward the UI reports progress or recovery, not a cancellation promise. Status and receipts survive through the private journal and trusted shell, with no secrets exposed. Readiness requires native binding of the destination job, process and component pair plus authenticated service response and compatible state read; legacy restoration instead proves the exact allowlisted original artifact/job and authenticated service/state readiness under its limited source contract. Neither path assumes an old service has a native OTA channel.

## Transaction and recovery

The following is a proposed service-only transaction, not a claim that existing adoption already supports all these cases. A capability must not be advertised until every phase and recovery branch is implemented and validated for its source and platform. Lock and journal formats must have a versioned discriminator; unknown variants fail closed. Existing transactions retain their original semantics.

1. **Inspect:** authenticate the session; independently capture source job, registration including disabled override, process incarnation and component identities, installation/home/port, destination bundle and helper identities, state compatibility and capabilities. Return an opaque candidate and revision. Inspection alone grants no authority.
2. **Consent and wait:** explicit user confirmation names the observed source and destination, explains that active work must finish and binds candidate, revision, installation, boot and authenticated desktop session. Record a bounded, revocable waiting intent and an idempotent receipt. Waiting does not stop work or reserve idle. Cancel is available while waiting. Expiry, session loss, reboot, identity drift, registration change or conflicting maintenance invalidates permission to begin effects; reacquire fresh inspection and consent. Durable recovery after effects is not durable permission to start them.
3. **Reserve:** atomically check durable task, session, launch and maintenance leases and acquire the shared cross-process admission reservation that excludes every supported source and direct CLI work entry point. An unknown or nonparticipating writer, or an unprovable idle state, blocks. Concurrent clients use revision checks and conflict responses; retries with the same request ID return the same receipt, and changed inputs or replayed/expired grants fail. Recheck consent, identities, compatibility and reservation under the appropriate locks immediately before preparation.
4. **Prepare:** persist intent and exact original registration and recovery identities in a private, atomic journal; verify signed destination/helper and arm independent native recovery before the first external effect. Capture no user-data snapshot for restoration. The helper independently verifies the scoped grant and reservation. If preparation cannot be proved, do not mutate.
5. **Switch:** journal intent before each effect and observed completion afterward. Recheck the exact job/process, source and destination identities and reservation; stop only the inspected job, prove exit, change only its registration to the bundled CLI, and start the destination. Never overwrite or delete the original source. A race or uncertainty enters recovery, not a blind retry.
6. **Verify and commit:** authenticate the new process and component identities natively, then verify authenticated service readiness and a valid compatible state read. Only then durably commit, release admission and retire recovery. The result is idempotent across retries. Once committed and accepting work, do not automatically roll back a successful transaction; subsequent repairs are new operations.
7. **Recover:** on failure or crash before commit, independent recovery replays the journal idempotently, restores the exact original registration and disabled override, and proves the original process/code identity and service readiness under the applicable source contract. Do not substitute another binary at the same path or restore stale user data. If proof or restoration fails, retain journal and recovery evidence, keep admission closed where enforceable, and surface recovery-needed guidance. After commit, recovery performs cleanup only. Recovery authority is limited to completing or undoing recorded effects, including after reboot; it cannot start a new reconciliation.

Atomicity and OS locking details must be proven against the actual adoption and OTA implementations, including crashes between intent, effect and observation. If those contracts cannot safely be reused, the capability remains unavailable until a separately reviewed extension exists. A reported zero work count from an unknown or older service is never an admission reservation.

## User-visible states

Show distinct, accessible text and actions for checking, verified match, compatible mismatch, waiting for work (with cancel), reserved/preparing, switching/verifying, success, expired/cancelled, restored after failure, and recovery needed. Explain whether work is still running and whether a change has begun; do not promise interruption-free behavior without the reservation. External, unverified, unknown identity, incompatible/newer, unsupported capability and platform states each show the relevant blocker and concrete management guidance. A missing peer field is “cannot verify build,” not “up to date.” Only an eligible candidate offers the explicit change action. Reclaim, if independently eligible under ADR 0011, uses its own clearly labelled confirmation and interruption warning, never the idle-only action. Accessible names, keyboard/focus, status announcements, narrow layouts and existing design-system controls follow UI rules; visual details require UI evidence rather than this document's approval.

## Migration and platform boundaries

Old services and desktops cannot gain native capabilities from a web response. Identify the installation method before suggesting a command; if unknown, ask the operator to identify the owner and consult its installation documentation rather than guessing. For a standalone CLI, finish tasks and terminal sessions, then use `pacer update` and, when appropriate, `pacer service restart`. For Homebrew use `brew upgrade pacer`; for npm use `npm install -g @lamtuanvu/pacer@latest`; after work finishes, restart the registered service with `pacer service restart` if appropriate to that installation. These are manual actions, not reconciliation, and a legacy update action can restart immediately; warn users to finish work first. An attached external service stays attached: ask its owner to use its own management procedure and do not offer a local takeover as the package-manager update. See [desktop update guidance](../desktop-updates.md#updating) and [distribution](../distribution.md). Add fields and capabilities without breaking old clients, and gate mutation on both sides actually supporting the full contract. Do not reinterpret existing journals or grants. macOS launchd signed-native support is the first candidate, separately verified on Apple Silicon and Intel; Linux service managers and other distribution channels receive detection/guidance until equivalent native ownership, exclusion and recovery are designed and validated. No remote service is changed by a local decision. Each paired machine has its own user, installation, process identities, capabilities, consent, reservation and journal; no identity or authority transfers between machines. Remote live testing requires separate maintainer approval.

## Verification and delivery gates

Implementation needs isolated tests for component identity, same-version divergent and unordered builds, independently built component pairs, dirty/unknown/malformed and old peers, incompatible/newer source, signing and metadata tampering, process/file drift and PID reuse; capability refusal and external ownership; concurrent clients, request replay, revision conflict, work-start races, cancellation, session/boot expiry; hostile service pages, missing API, unavailable service, reconnect and recovery-needed fallback presentation; managed and eligible legacy coordinator handoffs, process death and reboot at every reservation and journal boundary, exact restore, failed proof and retained gate; no user-data rollback; and separate OTA, adoption and reclaim paths. Use disposable `PACER_HOME`, no production credentials or services. Run affected automated checks and `bun run live` under [live validation](../testing/live-validation.md), with evidence for every changed behavior and surface (CT-11); explicitly report unexercised surfaces **UNVERIFIED**. Signed native release evidence must cover the applicable ADR 0001 signing policy (including its interim self-signed addendum, or Developer ID/notarization when required), both macOS architectures and reboot recovery; development fixtures do not prove those properties. Include UI-18 screenshots, implementer compliance and independent UI/accessibility and QA reports for UI changes, plus independent architecture, security and protocol assessment appropriate to the final implementation. REPO-10 requires independent project review of final changes, confirmed blocker fixes and independent review of those fixes. Required missing evidence is incomplete, not a pass; only the maintainer can grant a scoped exception or approve merge.

## Open product decisions

- Whether an eligible mismatch is offered automatically at launch or only in settings, and desired notification frequency.
- Exact confirmation copy and how much source identity to display without exposing unnecessary paths.
- Whether any future downgrade or busy-work handover should be supported; both require a separate compatibility and safety decision.
- Whether non-macOS native reconciliation is a priority and what supported service-manager/distribution combinations it should cover.

Until decided, use settings-based explicit consent, no downgrade or busy handover, and guidance only outside validated macOS support as conservative design defaults, not user-approved product decisions.
