# Plugin host core: protocol, lifecycle, operations and conformance on the TypeScript host

Status: design agreed 2026-10-19. Sub-project 1 of milestone M0 in the
[plugin system design](2026-10-19-plugin-system-design.md). Nothing is built.

## Problem

The plugin system design describes a minimal host and a versioned plugin contract, but
the repository has neither. Every adapter is still hard-wired, and extracting the first
one (usage readers, sub-project 2) needs a host to extract into: a protocol, a
manifest, a registry, a subprocess transport, operations to manage plugins, and a
conformance suite that will later judge the Rust host with the same cases.

Two facts about the code shape this sub-project:

- The release is one `bun build --compile` file, so bundled reference plugins cannot
  be separate executables. They run by re-executing the pacer binary with a hidden
  entry.
- The client API already has a `plugin.install` operation and `pacer plugin
  install|uninstall|set` commands for the Orca panel installer in `src/plugin/`. The new
  system takes the `plugin.*` namespace and leaves those untouched.

## Goal

A host that can discover, start, call, time out, restart and report plugins over the
subprocess transport, with nothing enabled by default, so user-visible behavior is
unchanged while the contract, tests and governance land together.

Done means:

- `pacer plugin list` and `pacer plugin doctor` work over the CLI and the API, with
  fixture plugins installed under the pacer home.
- The conformance suite passes against `bun src/cli.ts api --stdio` in `bun run test`
  on macOS and Linux, and imports no host code.
- `docs/plugin-protocol.md` and `docs/plugin-protocol.schema.json` are generated and
  freshness-tested.
- The ADR and constitution 0.4.0 are in the same PR.
- A fresh install behaves exactly as before.

## Non-goals

- `plugin.add`: archive download, publisher keys and signature checks are a separate
  distribution sub-project. Until then a plugin is installed by placing its folder under
  the pacer home, which is also how the conformance suite installs fixtures.
- Any real extension point or reference plugin. The usage reader arrives in
  sub-project 2 with the full TypeScript SDK.
- The Rust SDK, Rust types and the wasm transport (M1 and M3).
- A web app screen for plugins (surfaces sub-project); the CLI is complete on its own
  (ARCH-8).

## Decisions taken while brainstorming

| Question | Decision |
|---|---|
| Namespace | The new system owns `plugin.*` and `pacer plugin …`. The Orca panel's `plugin.install` op and `plugin install|uninstall|set` commands stay as they are. |
| Bundled plugin process model | Subprocess, by re-executing the pacer binary with `plugin run <id>`. Identical path, failure semantics and conformance for bundled and installed plugins. |
| Reference plugin granularity | One plugin per extension point (for example `pacer-usage` contributes every usage reader). |
| Rust types | M0 commits the JSON Schema; Rust types are generated from it in M1 where CI compiles them. |
| M0 slicing | Host first (this sub-project), then one extraction per PR, usage readers first and the Orca executor last. |

## 1. Scope and layout

| Path | Holds |
|---|---|
| `src/plugins/` | Host side. `protocol.ts`: zod schemas and `PLUGIN_PROTOCOL_VERSION = "1.0.0"`. `manifest.ts`: manifest schema and validation. `registry.ts`: discovery, enablement, grants and state. `process.ts`: spawn, framing, deadlines, cancel, backoff. `host.ts`: call an extension point; answer capability calls. |
| `src/core/plugins.ts` | Operation handlers, so `src/api/ops.ts` stays a registry (ARCH-2). |
| `packages/plugin-sdk/` | The plugin-side runtime `@pacer/plugin` as a bun workspace, unpublished until sub-project 2 completes it: stdio loop, handshake, typed capability client, `serve(handlers)`. This sub-project ships only what the fixtures need. |
| `plugins/` | Reference plugins, one folder per plugin with `pacer-plugin.json` and `src/main.ts`. `plugins/bundled.ts` lists them with lazy imports so `bun build --compile` embeds them. Empty of real plugins until sub-project 2. |
| `conformance/` | Host-neutral runner and fixture plugins. `test/plugin-conformance.test.ts` runs it against the TypeScript host. |
| `docs/plugin-protocol.md`, `docs/plugin-protocol.schema.json` | Generated by `scripts/plugin-protocol-doc.ts` (`bun run plugin:protocol`), freshness-tested (P11). |

`src/plugin/` (Orca panel installer) and `src/plugins/` (plugin host) are unrelated.
The old one is not touched.

## 2. Wire protocol

### Framing

Newline-delimited JSON-RPC 2.0 on the plugin's stdin and stdout, with the same framing,
1 MiB line cap and error mapping as `pacer api --stdio`. stderr is not protocol: the
host captures it to `$PACER_HOME/logs/plugins/<id>.log`. Both sides send requests, so
each side matches replies by id.

### Handshake

The first message is host to plugin:

```
plugin.hello  { protocol: "1.0.0", pacer: "<pacer version>", manifest, config, grants }
→ { protocol: "1.0.0", id, version, contributes: ["diagnostic", ...] }
```

The host checks that `id` and `version` match the manifest and that the plugin's
protocol major equals its own, and keeps only the extension points the plugin says it
serves. Anything else is a handshake failure, reported by `plugin.doctor`.

### Host to plugin

Methods are named `<extensionPoint>.<method>`. This sub-project defines one extension
point, `diagnostic`, with `diagnostic.ping → { ok: true, uptimeS }`. Every plugin serves
it through the runtime, and `plugin.doctor` uses it. Real extension points arrive with
their extraction sub-projects, each adding its schemas to `protocol.ts`.

### Plugin to host

Methods are named `capability.<name>` and are answered only when the manifest declared
the capability; otherwise the host replies `capability_denied` without acting. This
sub-project implements `capability.log` and `capability.config.get` (the plugin's own
config slice). The remaining capabilities are declared in the schema now and
implemented when a reference plugin first needs them: `fs.read` and `process.spawn`
with the usage readers, `net.http` and `secrets.resolve` with endpoint vendors,
`tasks.read` and `events.subscribe` with policy, `entitlement.report` with
distribution.

SDK capability clients always call the host, even for file reads, so phase 1 plugins
behave as they will under wasm and the host can refuse calls outside declared scopes.

### Deadlines

The host owns the timer. On expiry it sends the notification `$/cancel { id }`,
resolves the call with `plugin_timeout`, and leaves the process running. A later reply
to that id is dropped.

### Errors

Five new `CoreError` codes cross the client API (API-4):

| Code | HTTP | Meaning |
|---|---|---|
| `plugin_timeout` | 504 | A call passed its deadline. |
| `plugin_unavailable` | 503 | The plugin is disabled, refused, needs a grant, is failing, or exited mid-call. |
| `plugin_refused` | 422 | Manifest or handshake rejected. |
| `capability_denied` | 403 | Capability not declared or outside its scope. |
| `unknown_plugin` | 404 | No plugin with that id. |

### Versioning

`PLUGIN_PROTOCOL_VERSION` follows P4 independently of the client protocol. The
manifest's `host` field is a semver range checked at load.

## 3. Registry and lifecycle

### Discovery

Two sources, read at service start and on every `plugin.list`: the bundled list in
`plugins/bundled.ts`, and `$PACER_HOME/plugins/<id>/pacer-plugin.json`. A folder whose
manifest fails validation, whose id differs from the folder name, or whose `host`
range excludes the current protocol is listed as `refused` with the reason and never
loaded. An installed plugin with a bundled plugin's id is refused, so bundled plugins
cannot be shadowed.

### Enablement and grants

A `plugins:` section of the strategy file, edited through the same atomic write and
lock as other config:

```yaml
plugins:
  disabled: [pacer-usage]          # bundled plugins are on unless listed here
  installed:
    acme-policy: { version: "1.2.0", capabilities: [tasks.read, log] }   # the grant
```

Bundled plugins are trusted and enabled by default. An installed plugin is off until
`plugin.enable` records a grant for its current capability set. The CLI shows the set
and asks once; other surfaces do the same through the op. A new version that asks for
more capabilities drops back to `needs_grant`.

### States

Per plugin, in memory in the service process: `disabled`, `refused`, `needs_grant`,
`idle`, `starting`, `ready`, `failing`. Every change publishes an additive `plugin`
API event (API-1); entering `failing` also writes an activity entry.

### Process

Spawned lazily on the first call. Bundled: the pacer binary's own argv plus
`plugin run <id>`. Installed: `entry` resolved inside the plugin folder, argument vector
only (SEC-5), working directory the plugin folder. Environment is a clean minimum:
`PATH`, `HOME`, `PACER_HOME`, `PACER_PLUGIN_ID`, `PACER_PLUGIN_PROTOCOL`. Secret
injection by reference is added with `secrets.resolve`.

### Calls

Calls queue per plugin and run one at a time unless the manifest sets `reentrant`. A
call to a `disabled`, `refused`, `needs_grant` or `failing` plugin fails fast with
`plugin_unavailable`.

### Failure

| Event | Host behavior |
|---|---|
| Exit or spawn error | Pending calls fail with `plugin_unavailable`; restart after 1 s, doubling to 30 s. |
| Three restarts within 60 s | State `failing`, no further restarts. `plugin.enable` or a service restart clears it. |
| Deadline | `plugin_timeout` for that call only; the process is not restarted. |

### Shutdown

Service stop sends SIGTERM to every child, waits 2 s, then SIGKILL.

## 4. Operations and CLI

| Op | Params | Result and behavior |
|---|---|---|
| `plugin.list` | none | Every discovered plugin: `id`, `version`, `publisher`, `tier`, `bundled`, `enabled`, `state`, `contributes`, `capabilities`, `grant`, `error`. Read-only; starts nothing. |
| `plugin.enable` | `id`, `grant?: boolean` | For an installed plugin with no matching grant: without `grant: true` returns `needs_grant` with the capability set; with it records the grant. Clears `failing`. Publishes a config change. |
| `plugin.disable` | `id` | Stops the process and records `disabled`. |
| `plugin.remove` | `id` | Installed plugins only; a bundled id returns `not_allowed`. Disables, then deletes the folder and the grant. |
| `plugin.doctor` | `id?` | For each enabled plugin: starts it if idle, runs `diagnostic.ping` with a 5 s deadline, reports `ok`, protocol versions, served extension points, restarts in the last minute and the last error. Refused or mismatched plugins report the reason and the `host` range they need. |

`enable`, `disable` and `remove` take the strategy edit lock; a conflicting concurrent
change returns `conflict` (ARCH-3).

CLI: `pacer plugin list [--json]`, `enable <id> [--yes]`, `disable <id>`,
`remove <id>`, `doctor [<id>] [--json]`, and the hidden `plugin run <id>` entry used by
the host. `enable` on an ungranted plugin prints the capability set and asks for
confirmation unless `--yes`.

Live validation guard: `plugin.remove` joins the D8 refusal table because it deletes
folders under the home. `enable` and `disable` stay allowed; they edit only the sandbox
strategy.

## 5. Conformance suite and fixtures

### Runner

`conformance/run.ts` takes a host argument vector (`bun src/cli.ts` today,
`target/release/pacer` in M1). For each case it creates a temporary pacer home, copies
the fixtures the case needs into `plugins/`, writes a minimal strategy, starts
`<host> api --stdio`, and drives it with the client protocol only: `plugin.*` ops,
`diagnostic.ping` through `plugin.doctor`, and the `plugin` event stream. It imports no
host code, so the same suite judges the Rust host.

### Fixtures

One plugin program, `conformance/fixtures/plugin.ts`, built on the plugin-sdk runtime.
Its behavior comes from a `fixture.json` next to each manifest: `pingDelayMs`,
`crashAfterPings`, `exitAtStart`, `ignoreCancel`, `claimContributes`. Folders give the
variants: `good`, `slow`, `crasher`, `over-privileged` (declares `net.http` with no
grant), `old-protocol` (`host: "^0"`), `shadow` (a bundled plugin's id), `reentrant`.
The entry is the script with a `#!/usr/bin/env bun` line and the execute bit, so it
runs as an installed plugin wherever Bun is present.

### Cases

1. Discovery and listing: every variant appears with the expected state and reason.
2. Handshake: id, version and protocol major are checked; a wrong `contributes` claim is not served.
3. Lazy start: `plugin.list` starts nothing; the first `doctor` starts the process.
4. Deadline: `slow` returns `plugin_timeout`, the process survives, a later ping works.
5. Crash and backoff: `crasher` restarts; after three restarts in a minute the state is `failing`, calls return `plugin_unavailable`, `enable` clears it.
6. Capability denial: an undeclared `capability.config.get` gets `capability_denied`; a declared one answers.
7. Grants: `enable` without `grant` returns `needs_grant`; a version bump with more capabilities drops back to `needs_grant`.
8. Serialisation: two pings to a non-reentrant plugin complete in order; the reentrant one overlaps.
9. Logs: stderr lands in the plugin log file, never in stdout.
10. Shutdown: closing the host's stdin terminates children.

Policy fail-open, secret references and signed archives join the suite with their
sub-projects.

### Wiring

`test/plugin-conformance.test.ts` runs the runner against the TypeScript host in
`bun run test` on both CI platforms, one case per test with a timeout of about 20 s.

## 6. Generation, governance and testing

### Generated artifacts (P11)

`scripts/plugin-protocol-doc.ts` renders `docs/plugin-protocol.md` from the zod
schemas: handshake, extension points with methods, deadlines and result shapes,
capabilities with scopes, error codes, lifecycle states and the manifest. It also emits
`docs/plugin-protocol.schema.json` through `z.toJSONSchema`, the file M1 feeds to the
Rust type generator. `bun run plugin:protocol` writes both; `--check` backs a
freshness test. The client protocol doc is regenerated for the new error codes, ops and
event.

### Governance in the same PR

- ADR `docs/decisions/2026-10-19-plugin-host-and-rust-strangler.md`, in the existing
  date-named form and the layout of the clients ADR: context, decisions D1 to D6
  (minimal host; one contract, two transports; open core by tier; no entitlement checks
  in the host; strangler milestones; Rust CI required from M1), consequences, open
  questions.
- Constitution 0.4.0 with P13 (minimal host: every capability a plugin could provide
  is a plugin), P14 (the plugin protocol is versioned under P4's rule) and P15 (the host
  never checks entitlements). The dependency direction becomes clients → API → host
  core → plugin protocol → plugins. A decisions.md entry records the bump, and OD-3
  notes that Rust CI becomes required at M1.
- Architecture rules ARCH-12 to ARCH-14 mirroring the three principles, and
  context.md map rows for `src/plugins/`, `plugins/`, `packages/` and `conformance/`.
- A boundary verified by the core-boundaries test: nothing outside `src/plugins/` and
  `src/core/plugins.ts` imports from `plugins/`.

### Unit tests

Manifest validation and range checks; registry state transitions with a fake spawn, as
the stdio client tests do; deadline and cancel on the transport; grant round-trips in
config; each op's error paths; CLI output.

### Live validation (CT-11)

The PR changes runtime behavior. The sandbox runs `pacer plugin list` and `doctor`
over the CLI and the API with the fixture plugins installed in the sandbox home, plus
one disable, enable and remove cycle. TUI, web, Orca panel and desktop show nothing new
and are reported as not affected.

## Risks

- Bun start-up per plugin process is the main unknown. Sub-project 2 measures it on the
  usage readers.
- Fixtures depend on Bun on `PATH`, true in CI and on developer machines.
- `z.toJSONSchema` may not represent every schema feature the Rust generator needs. M1
  finds out, which is why the schema file is committed now.
