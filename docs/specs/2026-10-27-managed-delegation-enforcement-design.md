# Managed delegation enforcement

Status: Approved by maintainer conversation on 2026-10-27. Extends the intelligent work dispatcher design.

## Intent and guarantee

When Pacer starts an executor in **strict managed mode**, the executor's certified native subagent entry points must be blocked so they cannot create untracked execution children through those entry points. The executor can ask Pacer to create a child with `dispatch.child`; the service then authorizes, selects, launches and records it. The rule applies to every Pacer-launched local executor, regardless of which agent is the configured session planner. A missing or unverified blocking control prevents admission to strict managed work.

This guarantee covers supported native subagent entry points that an adapter has certified for the installed agent version. It is not a security boundary against an agent intentionally invoking an arbitrary AI CLI or provider API through a general shell tool. Pacer must display that limit and must not call hook-based control a universal process-level guarantee. Remote and Orca launches require separate certification; until then they are ineligible for strict managed work.

## Approaches

1. **Instructions and observation only:** keep executor prompts and record calls to `dispatch.child`. This preserves every executor but cannot prevent untracked native children. Rejected for strict mode.
2. **Certified adapter controls with fail-closed admission (selected):** each agent adapter blocks its native subagent operations, proves the block in the selected account and installed version, and reports a short-lived capability result to the host. This works with existing subscription CLIs, while excluding adapters that cannot establish control.
3. **Pacer-owned agent runtime:** Pacer brokers all tools and child-agent calls. This provides a common tool boundary, but changes how subscription CLI accounts are used and is a separate product effort. It remains an option if process-level control is required.

## Service contract

- The host owns one `delegationEnforcement` policy for a managed attempt: `strict` or `cooperative`. New managed roots default to `strict`, including roots submitted through a saved profile created before this feature. Already running or queued legacy tasks retain `cooperative` and are labelled as such. The release must certify at least one local executor on each supported platform before switching this default; if no certified executor is available for a particular account, the new work queues with a visible reason. Child attempts inherit `strict` and cannot weaken it.
- Before choosing or launching a candidate, the host requires a current enforcement certificate for the exact agent binary/version, account configuration, launch mode, launch flags, hooks or native permissions, and project overrides. The host owns the probe: in a disposable repository and session using that same launch path, it asks the agent to invoke each supported native child entry point and must observe either a synchronous hook denial or an explicit provider permission denial/tool unavailability, with no child start. A canary that never attempts the operation or cannot demonstrate the native path is blocked does not pass. The probe may use the selected account's quota, so setup reports that before running it. The certificate records covered entry points, input fingerprint, probe evidence, time, expiry (at most 24 hours) and unsupported reason. Adapter declarations and installed config files alone are insufficient.
- In `strict`, a candidate without a current passing capability result is ineligible. The decision engine receives only eligible candidates and cannot waive this constraint. If none remain, work queues with a visible reason; it never silently becomes cooperative. Candidate eligibility is checked again immediately before launch.
- Every strict attempt receives a separate random, attempt-bound **enforcement token**, stored only as a hash by the service and passed to its own guard process. The guard validates it against the live attempt before returning a synchronous denial for native execution-subagent calls, with a direction to `dispatch.child`. Missing or invalid identity, unknown payloads, host errors and timeouts in strict mode deny the native child call. The enforcement token has no child-delegation authority. The guard may allow documented read-only helper types only if the adapter proves they cannot perform execution work; otherwise it denies them too.
- A distinct work grant remains necessary for `dispatch.child`. The service enforces subtree, depth, count, concurrency, inheritance and replay rules as already specified. `PACER_ROLE=executor` and `PACER_TASK_ID` are labels, not credentials. An attempt without `allowDelegation` gets the enforcement token but no work grant; its native execution-subagent calls are still denied in strict mode. Both tokens are revoked at attempt end and excluded from logs and reports.
- Recheck the certificate fingerprint and expiry immediately before launch. A changed binary, account folder, hook or project override invalidates it and requires a new probe. Emit attempt-scoped `enforcement.checked` and `native-child.denied` events; emit `enforcement.lost` only when a concrete invalidation or guard failure is observed after launch. Stop admitting further children then and label the attempt's native-subagent control **UNVERIFIED**. A hook disabled inside an already running closed-source agent may not be observable, so this is an admission-time certification, not a continuous guarantee. Store the policy, adapter/version, certificate and observed loss with the dispatch decision. Do not log tokens, credentials or full subagent prompts.

## Adapter implementation order

1. Claude Code: change the existing `Agent|Task` guard so executor sessions in strict mode receive a denial, then verify the selected account and actual host invocation with a live probe.
2. Codex: test whether the installed version invokes the configured `spawn_agent` pre-tool hook and honors a synchronous denial. Config presence alone does not certify it.
3. Cursor: test whether `subagentStart` can actually prevent creation. If it only reports after creation, Cursor remains unsupported in strict mode.
4. OpenCode: apply its documented native task/subagent permission deny in the Pacer-launched environment, then verify it for the installed version. The current instruction-only integration remains cooperative until that probe passes. Other agents need their own blocking interface and probe.

Each adapter owns its native interception and probe logic through a versioned plugin capability. The Pacer host owns admission, grant validation, dispatch and history. A plugin cannot certify another adapter or change the host's strict policy. An account or agent update invalidates the previous probe. Pacer should expose a read-only diagnostic showing the exact account/version, last probe and unsupported reason in the CLI and Dispatcher UI.

Implementation observation for Claude Code 2.1.281: its native initialization advertises `Task`, while the structured stream reports the invoked tool as `Agent`. The host accepts that alias only when the same canary advertises `Task` and does not advertise a separate `Agent` tool, and the matching tool result reports the Pacer denial as an error. A hook marker alone never certifies the path.

## Validation and rollout

Use isolated accounts and disposable repositories. For each certified adapter, exercise an actual native child request and verify denial, then request a child through `dispatch.child` and verify its work-tree lineage. Exercise disabled hooks, changed account folders, agent upgrades, malformed inputs, timeout, unavailable service, concurrent attempts and a child grant that has expired or been revoked. Verify that an uncertified adapter is excluded before launch and that the UI says why. Record untested native versions and launch modes as **UNVERIFIED**, not supported.

Runtime implementation requires API/protocol, security, architecture and QA review under API-1–5, SEC-1/5, ARCH-1/2/5/12, CT-4/11 and REPO-10. It retains cooperative behavior only for tasks already admitted before the release. Strict exclusion is shown in preview and eligibility reasons for new work. The default change needs a migration and release note, plus an update to ADR 0006 before implementation.
