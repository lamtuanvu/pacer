# M2 P3-A SQLite binding proof

Status: proof only, 2026-11-01. This does not transfer a public operation or the task store to Rust. It follows the SQLite task-store decision and ADR 0015. RUST-8/9 remain proposals.

## Existing contract and consumers

`src/tasks/store.ts` owns `state/tasks.db`, the `tasks` and `task_first_settle` tables, `tasks_state`, `tasks_updated_at`, `tasks_created_at`, and `tasks_retention` indexes. It migrates older `tasks` tables by adding `json_mtime` and `archived`. Connections use WAL, 5 second busy timeout, and normal sync. Create and update write compatibility JSON before committing the immediate SQLite transaction. Import accepts only valid task JSON, preserves files, and refuses lower revisions. A cached connection reopens on inode change; directory stamp, `data_version`, and `total_changes()` govern import and invalidation. The `orca/task-<id>.lock` file serializes cross-process mutations; preparation also blocks process-local conflicting synchronous writes before a reentrant final commit.

`src/dispatch/store.ts` creates `work_nodes`, grants, enforcement tokens/certificates, events, decisions, reservations, observations, refresh, reviews, retry requests, waits, dependency waivers, learning exclusions/reset, and `attempt_usage`, plus indexes and five triggers on `tasks`. The triggers append task change events, revoke grants/tokens, and maintain queue/capacity waits. `src/dispatch/{work,enforcement-token,learning,refresh}.ts` mutate these tables; `readonly.ts` opens the same file read-only. `src/tasks/{api,runner}.ts` join dispatch and task transactions, including creation claims and decisions. `src/dispatch/{runtime,enforcement}.ts` consume the same state.

`src/messaging/store.ts` creates `messages` and `msg_turns` with request, recipient, task, turn, and root indexes; its in-place migration adds `messages.fingerprint`. `src/messaging/liveness-store.ts` creates `msg_liveness` and adds `nudges` to old tables. `src/messaging/{broker,hooks,liveness,turns,send,policy,publish,live,participants}.ts` consume message state and task revision/locks. Other direct users of `taskDatabase` are `src/session/create.ts`, `src/attachments/store.ts`, `src/assistant/store.ts`, and `src/tasks/api.ts`; the latter three create additional tables (`work_requests`, attachment, and assistant state). The wider task-store caller inventory includes API ops/events, CLI/core task and dispatch paths, runner/drain/retention/handover/cleanup, service running-work, session, plugin executor/host issuers, remote execution, insights and token rollups. These consumers must remain on the same database and lock protocol when P3-C moves the adapter.

## Binding and proof

Choose `rusqlite` 0.41 with `bundled` SQLite for the eventual adapter. `rusqlite` is a safe Rust API over `libsqlite3-sys`; the proof contains no application `unsafe`. Its current base requires SQLite 3.45.3 or newer, so relying on the host's system SQLite is unsafe for macOS distribution and unknown Linux images. Bundling pins the SQLite implementation in each supported binary and avoids a runtime system-library minimum. The C dependency increases build cost; CRATE-9 timings below are the initial measurement. Source: [rusqlite upstream documentation](https://github.com/rusqlite/rusqlite#usage).

The local proof observed Bun SQLite 3.54.0 and bundled Rust SQLite 3.54.1. Logical schema and row parity passed across this version difference; exact library-version equality is not a requirement.

The proof caught a millisecond rounding mismatch: `as_secs_f64() * 1000` differed from Bun's `stat.mtimeMs` by one floating-point step. Bun then reimported an equal-revision record, and the dispatch trigger path could report a unique-key conflict. The writer now calculates `seconds * 1000 + nanoseconds / 1,000,000`; the test asserts exact stored/file mtime equality on each alternation. P3-C must retain that exact representation.

The `pacer-sqlite-proof` crate is a disposable CLI test tool, not a production store. It requires a disposable-home marker, opens Bun's database with the same pragmas, snapshots `sqlite_master` and logical rows, and increments an existing record under `pacer-foundation`'s exact lock-file protocol with an immediate transaction and atomic JSON write-through. `test/sqlite-cross-runtime-proof.test.ts` alternates Bun and Rust writers on isolated homes, compares schema, rows, revisions, trigger effects, shared message rows and JSON, migrates an older schema, imports newer/stale JSON, reopens after database replacement, and checks an async Bun preparation conflict while Rust waits for its lock. It compares logical data, never database or WAL bytes.

## Gate

GO for the binding and the next P3-C adapter implementation on the tested macOS host architecture. This is not a gate for native task operation cutover: complete migration/consumer parity, failure injection, and platform validation still belong to P3-C. Linux arm64/x64 and the other macOS architecture are **UNVERIFIED**. No native operations or forwarding ledger rows change in this proof.

CRATE-9: first proof build with new dependencies took 20.67 s wall (the first compile failed on an import; the subsequent corrected leaf compile took 0.39 s wall). A clean before/after workspace baseline was not available without clearing the shared build cache, so the full CRATE-9 comparison is **UNVERIFIED**. Cargo timing HTML is in the shared target's `cargo-timings/` directory; that untracked machine-specific location is deliberately absent here.

Verification on macOS arm64: `cargo fmt --all -- --check`, `cargo clippy -p pacer-sqlite-proof --all-targets --locked -- -D warnings`, `cargo test -p pacer-sqlite-proof --locked`, `cargo xtask gen --check`, `cargo xtask loc --check`, `cargo xtask deps`, `bun run typecheck`, and 51 focused Bun tests passed. The Rust crate has no isolated unit tests; the four cross-runtime Bun cases execute its binary. CT-11 does not apply because this proof is not linked into runtime behavior. Independent REPO-10 review remains pending with the planner.
