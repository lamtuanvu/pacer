# Homebrew cask for the desktop app

Date: 2026-11-22

Status: Draft for maintainer approval.

Context: [ADR 0021](../decisions/0021-single-installation-owner.md), [distribution](../distribution.md), [desktop updates](../desktop-updates.md), [release rules](../../.project/rules/release.md) (REL-9).

## Intent

Let macOS users install the pacer desktop app with Homebrew:

```sh
brew install --cask lamtuanvu/tap/pacer
```

This is another way to get the same signed app that the DMG ships, not a separate build. After installation the app keeps updating itself through its own updater, exactly as a DMG install does. Homebrew installs it, uninstalls it and can reinstall it, but it is not the update channel.

## Goals

- The stable release workflow publishes `Casks/pacer.rb` to `lamtuanvu/homebrew-tap` automatically, next to `Formula/pacer.rb`.
- The cask points at the existing per-architecture DMGs (`desktop-pacer-<v>-darwin-{aarch64,x86_64}.dmg`) with their SHA-256 values. No new build or signing work.
- The in-app updater and Homebrew never move the app to an older version, and never fight each other.
- The cask keeps ADR 0021's one-owner rule: a machine never ends up with both the CLI formula and the desktop app each believing they own `pacer`.

## Non-goals

- Submitting to the official `homebrew/cask` repository. That needs a notarized Developer ID build. It is a later step, after the Developer ID bridge release described in [distribution](../distribution.md).
- Linux desktop packages via Homebrew.
- Nightly casks. REL-9 already rules out Homebrew for nightlies.
- Changing the CLI formula, apart from the conflict declaration below.

## Anti-goals

- `brew upgrade` (greedy or not) breaking a working installation: removing the service, agent hooks or the `pacer` command as a side effect of an upgrade.
- Homebrew downgrading an app that already updated itself.
- Anything in development or tests touching the real `/Applications/pacer.app`, `~/.pacer`, `~/.local/bin/pacer` or `com.pacer.serve` (AGENTS.md).

## Constraints

- **Signing.** Desktop builds are currently signed with the interim self-signed certificate (`PACER_SIGNING_CERT_SHA1`), not notarized. Homebrew no longer offers `--no-quarantine`, so a cask install carries the quarantine flag and the user approves the first launch once (System Settings › Privacy & Security › Open Anyway), the same as a DMG download. In-app updates do not add quarantine and stay prompt-free. A fresh copy written by `brew reinstall` or `brew upgrade --greedy` is quarantined again and will prompt again until builds are notarized. This is documented, not worked around.
- **Ownership (ADR 0021).** The formula owns `pacer` at `$(brew --prefix)/bin/pacer`. The desktop, after Welcome/Consent, owns `~/.local/bin/pacer` (a link to `Contents/Resources/pacer`), the service and updates.
- **Publication order.** The desktop feed (`stable.json`) advances only in `desktop-publish`, after both signed architectures pass. The cask must never point at a version the feed has not published.
- **Tap token.** The existing `HOMEBREW_TAP_TOKEN` already has write access to the tap. The cask job reuses it and skips with a notice when it is missing, like the formula job.

## Approaches considered

1. **Cask conflicts with the CLI formula (chosen).** The cask declares `conflicts_with formula: "pacer"` (the tap-qualified form if Homebrew requires it), and the formula declares the matching cask conflict. A user who has the formula is told to `brew uninstall pacer` before installing the cask. The app then sets up its service and command through its normal Welcome/Consent flow, keeping settings and tasks in `~/.pacer`. One owner, no PATH shadowing, and no new takeover code.
2. **The app takes over the formula's command.** The app would detect a Homebrew formula install and replace or shadow `$(brew --prefix)/bin/pacer`. Rejected: it writes into Homebrew's own prefix, and the next `brew upgrade pacer` or `brew cleanup` silently undoes it, which is the "two owners fight" situation ADR 0021 exists to prevent.
3. **The cask also links a `binary`.** A `binary "#{appdir}/pacer.app/Contents/Resources/pacer"` stanza would put `pacer` in `$(brew --prefix)/bin`. Rejected: the app already links its own command after consent, so this would create a second, brew-owned copy of the command that the app's owner record does not know about.

## Design

### Cask contents

`Casks/pacer.rb`, generated by the release scripts:

- `version` and per-architecture `url` and `sha256` (`on_arm` → `aarch64` DMG, `on_intel` → `x86_64` DMG). No existing metadata records the DMG hashes (`desktop-release-<v>.json` has none, and the feed hashes only the `.app.tar.gz` update archives), so the cask job computes them from the exact DMG files it publishes: on a tag push, the assets downloaded from the GitHub release after `desktop-publish`; on a dry run, the `desktop-signed-*` build artifacts. (My call: this keeps the change out of the signed feed schema.)
- `name "pacer"`, `desc` matching the formula, `homepage`.
- `depends_on macos: ">= :big_sur"`, matching `minimumSystemVersion` 11.0 in `tauri.conf.json`.
- `auto_updates true`, so plain `brew upgrade` leaves the app alone and the in-app updater stays in charge.
- `app "pacer.app"`.
- `conflicts_with formula: "pacer"`.
- `uninstall quit: "dev.pacer.desktop"` only. The cask's uninstall stanza does **not** unload `com.pacer.serve`, delete the command link or remove agent hooks, because Homebrew also runs uninstall steps during `brew upgrade --greedy` and `brew reinstall`, and those must not tear down a working installation (anti-goal). Full removal stays `pacer uninstall --all`, which the cask's `caveats` names.
- `zap` removes only the app's own macOS caches, preferences and saved state for `dev.pacer.desktop`. It never removes `~/.pacer` (tasks, settings and accounts). The exact paths are for the builder to list from what the app actually writes.
- `caveats`: the first-launch approval while builds are self-signed, that the app updates itself, and that `pacer uninstall --all` is the full removal.

### Switching from the CLI formula

`brew uninstall pacer` removes only the brew binary. A formula user who ran `pacer init` still has a `cli` owner record, possibly a `~/.local/bin/pacer` link and a `com.pacer.serve` registration that now points at a missing binary. The documented switch is: `brew uninstall pacer`, then `brew install --cask lamtuanvu/tap/pacer`, then accept Welcome/Consent. `claim_desktop_ownership` writes the desktop record unconditionally, and the takeover moves the service registration to the bundled CLI. The plan must verify in a sandbox (temporary `HOME`/`PACER_HOME`, fixture bundle, separate port) that the consent and takeover succeed when the recorded CLI owner's executable and the registered service binary no longer exist. If they don't, fixing that is part of this work, not a follow-up.

### Formula change

`Formula/pacer.rb` gains `conflicts_with cask: "pacer"` so the conflict is reported from either side.

### Name

The cask token is `pacer`, the same as the formula. Homebrew keeps formulae and casks in separate namespaces, so `brew install lamtuanvu/tap/pacer` keeps installing the CLI and `brew install --cask lamtuanvu/tap/pacer` installs the app. The conflict means a user never has both installed, so `brew uninstall pacer` is never ambiguous. (My call. If ambiguity warnings turn out to be noisy in practice, `pacer-desktop` is the fallback token.)

### Generation

Extend `scripts/release/homebrew.ts` (or add `scripts/release/homebrew-cask.ts` beside it) with a cask generator that takes the version and the two DMG paths, hashes them and writes the cask. It refuses to write a cask unless both architecture DMGs and their SHA-256 values are present, mirroring the formula's all-platforms check. Tests go next to `test/release-homebrew.test.ts`: exact output for a fixture manifest, refusal on a missing architecture, and `ruby -c` syntax check.

### Release workflow

A new `homebrew-cask` job in `release.yml`:

- `needs: [verify, desktop-build, desktop-publish]`. `desktop-publish` runs only on tag pushes, so the job's `if` branches: on a stable tag push it requires `desktop-publish` to have succeeded (the feed has advanced) and hashes the released DMGs; on a dry run (PR or `workflow_dispatch dry_run`) it requires `desktop-build` to have succeeded, hashes the signed artifacts, prints the cask and syntax-checks it, and never pushes. Stable channel only.
- Reuses `HOMEBREW_TAP_TOKEN`, the push-permission check, the signed-off commit to the tap's `main`, and the skip-when-unchanged behavior of the formula job. A dry run generates, prints and syntax-checks the cask without the token.
- The CLI formula job is unchanged and still does not depend on desktop jobs (the existing "CLI/npm/Homebrew/plugin jobs never depend on desktop completion" rule). A desktop failure therefore leaves the cask at the previous version, which matches the feed.
- Not added to the `nightly-failure` job, which only reports nightly runs; the cask job never runs on nightlies.

The cask is bumped at the same point the feed advances, so Homebrew never offers a version the in-app updater has not, and never offers an older one.

### Coexistence with the in-app updater

- The app updates itself in place in `/Applications/pacer.app`. Homebrew's recorded version then lags (`brew list --versions` shows the installed-by-brew version). This is expected for `auto_updates` casks and harmless.
- `brew upgrade --greedy` reinstalls the cask's current version, which is never older than the feed. It quits the app first; it does not touch the service, command or hooks.
- Existing DMG users who switch to Homebrew run `brew install --cask --adopt lamtuanvu/tap/pacer`. `--adopt` takes over the existing `/Applications/pacer.app` without replacing it.

### Documentation

- `docs/distribution.md`: a Homebrew cask row, and the tap setup note that the same token now also writes `Casks/`.
- `docs/install.md` and `desktop/README.md`: the cask install command, the first-launch approval, the formula conflict and how to switch (`brew uninstall pacer`, then install the cask), and `--adopt` for DMG users.
- `README.md`: correct the stale line saying the tap "has not been created".

## Validation

- Unit tests for the generator as above; the release workflow tests (`test/release-workflow.test.ts`) assert the new job's `needs`, channel gating and token handling.
- A PR dry run of `release.yml` prints the generated cask and passes `ruby -c`.
- Live check without the real install: a local test tap (`brew tap-new` in a temporary `HOMEBREW_*` sandbox or a throwaway tap name) installing the cask from a fixture DMG with `--appdir` set to a temporary directory, then `brew uninstall`, confirming the uninstall stanza only quits the app. It must never use the real `/Applications`, `~/.pacer`, `~/.local/bin/pacer` or touch `com.pacer.serve`. The first real end-to-end install from the published tap happens on the maintainer's machine after the next stable release; until then that surface is UNVERIFIED.

## Left to the builder

- Whether the cask generator lives in `homebrew.ts` or its own file.
- The exact `zap` paths, from what the app writes under `~/Library`.
- Whether Homebrew needs the tap-qualified form in `conflicts_with` for a same-tap formula.
- The precise source of the DMG SHA-256 values in the desktop metadata.

## Later

- After a notarized Developer ID release: drop the first-launch caveat and consider submitting `pacer` to `homebrew/cask`.
- Consider an uninstall handback (ADR 0021's "uninstalling the desktop hands ownership back") once the app implements it, wired so it runs only on a real uninstall, never during an upgrade.
