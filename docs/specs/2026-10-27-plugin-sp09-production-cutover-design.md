# Direct executor production cutover design

## Intent

Move an admitted direct attempt from the built-in `src/exec/direct.ts` owner to the bundled `pacer-exec-direct` provider. The host continues to choose the executor, enforce policy, persist task state, resolve credentials and authorize each effect. The provider owns the attempt sequence and returns the existing complete `AttemptOutcome`. Local and remote runs preserve run-directory contract v1 and current delegate, attach, report, stop, retry and review behavior.

This extends [the extraction design](2026-10-19-plugin-extraction-design.md#9-direct-executor-pacer-exec-direct). The earlier staging contracts and isolated tests are prerequisites, not proof of production ownership.

## Approaches

The chosen approach is provider orchestration with host-issued fixed effects. A plugin call cannot grant itself a process command, Git write, file path, SSH host or secret. The host binds each grant to the persisted task, attempt, selected provider, canonical repository and run identity and rechecks that binding at the effect. Keeping `runAttempt` in the host behind a plugin call would leave the adapter unextracted. Moving raw `Bun.spawn` and endpoint key bytes into the plugin would weaken the host boundary. Neither is used.

## Contract and authority

`executor.run` returns the complete attempt outcome consumed by `src/tasks/runner.ts`. The provider receives a bounded, credential-free task and runner projection. A read-only resume arm on the same method observes the already-persisted run; it cannot claim or start another wrapper. Run-directory v1 remains readable by the current task log, viewer, takeover and retention code. Generated protocol docs, JSON Schema and Rust area types describe the wire contract.

Local effects include worktree creation/reuse, prompt publication, child start and supervisor reads. Each is issued for one exact operation and canonical path. The existing detached start grant is extended only for named pipe, interactive and takeover modes that production needs. Child environment secrets are resolved by the host at spawn from references; they never enter the plugin request, progress event, log or an `env.json` file. A plugin launch reply that is missing after a possible spawn is uncertain and cannot authorize another launch.

Before creating a local attempt directory, the host durably claims its exact task, attempt, provider, executor, workdir and path. It publishes `task.run` and clears the claim in one task update. A restart may recover an exact private, empty claimed directory; an unclaimed existing directory or one containing process markers refuses. A prelaunch stop can clear the claim because no run was published and the start broker requires that published run.

Plugin protocol 1.7 adds `capability.process.claimRun`. The call accepts only task and attempt; the host resource fixes provider, workdir, executable, argv and environment. For an isolated attempt, the same owning call must first consume its one-use worktree creation grant. Claim publication binds a one-use start grant to the resulting run directory and canonical workdir. A durable start intent precedes the wrapper effect; a lost start receipt cannot produce a replacement launch.

Worktree effects use a distinct consented `worktree` capability, added in plugin protocol 1.6.0 without removing 1.5 fields or methods. The provider may request bounded `inspect` and `resolveBase` reads for its exact task and attempt, then one `createOrReuse` effect for the approved base. The host derives the canonical repository, worktree path and `pacer/<task>` branch from persisted state; plugin input cannot supply a path, branch or Git argv. Immediately before mutation, the broker rechecks repository and task identity, approved base and existing worktree ownership. It atomically persists an exact placement intent before `git worktree add`. A lost reply may recover only that same placement: an existing foreign worktree, changed branch/HEAD, different base or replaced path refuses without a second effect. The host keeps the journal until the run is durably bound to that placement. After a verified run settles, a later attempt or retry may pin the prior task-owned worktree's current HEAD, preserving its commits while refusing any drift after the new grant is issued. Owner-owned legacy worktree parent directories can be made private through a verified descriptor; symlinked `PACER_HOME` is accepted only while its original canonical target stays pinned. Old installed manifests remain valid and cannot call the new methods without reviewed `worktree` consent.

For default new placement with an origin, a separate host admission journals the exact provider, attempt, repository and origin fingerprint before fetching that configured origin. It then records the resolved base commit and issues the worktree grant for that commit. A lost or timed-out fetch without a recorded commit stays uncertain and cannot automatically fetch again for the same attempt. A local-only repository preserves the existing automatic HEAD choice without a fetch. Explicit HEAD, named-base and same-owner retry placements also resolve locally. A retry may reuse the prior task worktree after its HEAD advances, while the same attempt still refuses branch or HEAD drift.

Remote effects use the reviewed SP08 configured-host issuer and fixed scripts for PREPARE, START, run reads, STOP, session streaming and transfer. An unavailable or uncertain provider never falls through to direct SSH. Remote grant identity is the exact persisted task, attempt, host, repository mapping and run directory. The approved disposable SSH checkout may be used only for CT-11 and is not production configuration.

### Remote pipe attempt handoff

The first remote production checkpoint covers a configured, noninteractive pipe attempt. The provider drives placement, launch, observation, stop and final transfer through separate host capabilities; there is no whole-attempt capability that simply invokes the old host runner. The host continues to own configured-host policy, fixed SSH scripts, credential selection, local run-directory mirroring and Git bundle publication. PTY/full-session viewing and managed child routes remain outside this checkpoint until their matching contracts are reviewed.

Before PREPARE, the host persists an intent for task, attempt, provider, executor, host alias and configuration fingerprint, canonical local repository, origin and configured remote checkout, selected base commit and branch. It issues only the SP08 fixed PREPARE tuple. A missing PREPARE reply never reissues PREPARE: a distinct read-only `PREPARE_RECOVER` fixed script may return the existing worktree only when it proves the expected checkout, branch, base HEAD and clean state. It performs no second fetch or creation. Missing, partial, foreign, dirty or advanced state is uncertain and refused. The chosen remote branch and worktree are then published in `task.run` before START. If publication fails, the intent remains for exact recovery; it never authorizes another placement.

START consumes one grant derived from that persisted run and writes a durable start intent first. A missing START receipt does not reissue START. REPORT and bounded read operations may only observe the exact run/host fingerprint; they keep `running`, `exited` and `uncertain` distinct. STOP uses the existing pending-stop identity and verifies remote exit before terminal settlement. After verified exit, the provider requests the host's bounded PREFLIGHT and bundle-transfer operations; the host retains the 50 MiB and 1–500 commit checks and branch compare-and-swap. No plugin receives raw SSH argv, secret bytes or a writable local Git path.

Protocol 1.9 adds `hosts.prepareOwned`, `claimOwned`, `startOwned`, `pollOwned`, `readOwnedOutput`, `stopOwned` and `transferOwned`. These methods are available to the bundled direct executor only with an exact call resource; generic host broker methods remain denied to it. The runtime selects the provider-owned route for noninteractive remote pipe tasks. A verified `missing-base` PREPARE response permits one journaled bundle retry; an unreceipted PREPARE enters read-only recovery. A stop remains pending until fixed STOP and REPORT prove exit. The host journals the exact local branch destination before bundle import, allowing a lost transfer reply to reconcile only the same run, branch and head.

## Durable stop and recovery

An active provider-owned task uses additive `stopPending` intent with attempt, requested time, provider ID, reason and bounded grace. `task.stop` and `dispatch.stop` return the truthful running task with pending stop immediately; they do not claim a process has exited. `task.wait` settles only after verified exit. The runner and start broker see pending stop before any new launch or retry. If the stop preceded spawn, they settle stopped without a child. Otherwise, `executor.stop` consumes a one-use host grant for the exact persisted wrapper or remote run and has a finite grace plus 5-second deadline. A provider deadline records the same durable stop machinery with reason `deadline` and settles failed after verified exit; a user stop settles stopped. Admission uses the current task revision, while completion checks the persisted run fingerprint, attempt, provider, directory/PID and pending-stop identity: unrelated progress revision changes must not turn a verified exit into an uncertain one. A refusal or lost receipt leaves intent durable.

On restart, a journaled worktree effect or empty run-directory claim with no published run resumes the same prepared attempt; the broker reuses only its exact placement and refuses foreign state. An already-published run instead resumes read-only and inspects its `running`, `exited` or `uncertain` state. A confirmed running run may receive another bounded stop grant for that same run; a confirmed exit may settle; uncertainty stays pending and forbids replacement launch. Session end and attach honor the same state. A retry can start a new attempt only after the previous attempt has a confirmed exit and the existing policy allows retry.

## Interactive and conversation completion checkpoint

The noninteractive local and configured remote pipe routes are production checkpoints, not the end of SP09. The extraction contract also names local interactive attempts, conversation sessions, attach, answer, takeover and remote PTY/full sessions. At the current checkpoint, `src/tasks/runner.ts` still selects the built-in `src/exec/direct.ts` for conversation, excludes a local runner whose session is `interactive`, and excludes remote full/PTY sessions. Those are remaining SP09 routes under P13 and ARCH-12. Local managed child attempts and same-task retries now use the bundled direct provider. Remote managed child delegation is an existing product limitation: remote executors have no scoped child grant (see `docs/dispatch.md`), so this work does not grant one implicitly or count its absence as a regression in the prior remote route.

The smallest shared prerequisite is a **local interactive attempt** with an otherwise ordinary task. This checkpoint does not select conversation or remote PTY yet. It extends the existing `executor.run` owned-local arm and exact `claimRun`/`startRun` authorities with a host-issued session kind, rather than allowing a plugin-supplied process mode, argv, path or environment. The host derives the interactive launch and bounded report hook from the selected runner, pins its executable and working directory as for pipe attempts, persists the run with its interactive mode before effect, and issues one-use start authority for that run. The plugin chooses when to claim, start, poll and return the complete outcome. Only the exact issued interactive grant may cause `startRun(..., session: "interactive")`; pipe grants cannot be upgraded by request parameters. The plugin never receives credential values or a work grant in RPC.

An interactive poll is not a pipe poll with a different flag. The host's fixed run-directory readers remain authoritative for `interactive.json`, report and transcript files, bounded output, session recording and exit. A `done`/`failed` report on a live wrapper permits one host-issued report-completion operation: the host rechecks the exact task/run, report identity and status, stops and reaps that wrapper, and returns a receipt containing the report status and recorded exit. The provider may settle the logical outcome from that receipt, as the existing `supervise` reported-completion path does; it cannot call the ordinary user-stop capability or claim success from a report string alone. `needs-input` and `turn-ended` keep the session attachable. A recorded exit with no completion report is a verified failed interactive attempt under the current rule, even when the wrapper exit code is zero, and may use normal retry policy. A dead wrapper without a recorded exit or a lost report-completion receipt remains uncertain and cannot authorize a replacement launch. Deadline handling must retain a durable stop intent and verified exit before settlement. The host binds the returned outcome to the persisted task, attempt, provider, run directory, interactive mode, worktree and observed report-completion/exit receipt. A user stop request remains `stopPending` until the provider's exact stop receipt and recorded run exit; attach and answer continue through the existing public session operations and run-directory contract. No plugin refusal or disablement invokes the built-in direct path.

The next checkpoint builds conversation on that same interactive owner: the existing `pacer-agent-session` adapter remains the authority for native identity and launch preparation; the host passes only an exact, bounded, host-issued launch to the executor provider. Conversation identity, attachments, native permission policy and task conversation activity must be persisted and revalidated against the same run before launch and on recovery. Takeover is a distinct continuation of the same attempt with its own run directory and exact session ID; it needs a separate one-use grant and recovery tests before route selection changes. Remote full/PTY uses the SP08 bounded session stream and its configured host grants, not the local process grant. These later routes require separate source review and live evidence before deleting the built-in attempt owner.

### Conversation continuation authority

A conversation is a persistent interactive run, not an ordinary interactive task whose `done` report ends the attempt. The host selects `conversation` only for a task durably marked `interactionMode: conversation` and a configured local runner. It persists that mode and the exact native agent-session identity in the same run claim before issuing a one-use start grant. The provider cannot request conversation mode, change a native identity, supply an executable, or name an attachment path. A pipe or ordinary interactive grant cannot be promoted by plugin parameters. A disabled/refusing provider leaves the task pending or failed under the existing state rules, with no built-in launch.

The host obtains capabilities, native identity and launch preparation from the consented `pacer-agent-session` adapter, using the selected account and workspace. This preparation must produce a bounded, immutable launch plan before run claim; it may not create files in the future run directory. Attachment claims are resolved and checked against the exact task and draft immediately before plan issuance, and the resulting adapter argv and reporting source are validated and pinned in the host grant. The broker publishes fixed private reporting files only after the run and start intent are durable, using the same no-replace atomic creation as the ordinary interactive hook. OpenCode's `report-plugin/index.ts` needs a separately named, size-bounded grant entry; its source remains adapter-owned and the host keeps account configuration bytes outside plugin RPC. Missing or changed attachment, identity, source executable or directory identity refuses the start without retrying through `src/exec/direct.ts`.

Native identity creation is an effect separate from executor launch. Assigned Claude and existing resume IDs can be journaled before claim. OpenCode `session.create` can lose its reply after creating a native session: the host records an exact identity intent before that command and must not issue a second create on restart if the reply is missing. A known ID is recovered only through the adapter's exact read-only lookup. An unknown ID remains uncertain and needs explicit operator recovery; it cannot be replaced by a newly created session. Once an ID is known, it is persisted with task conversation state and matched to the claimed run on every resume.

The provider observes the exact persisted wrapper and bounded session status until a recorded exit or verified stop. `done`, `failed`, `turn-ended` and `needs-input` reports are turn activity, not terminal completion; they do not invoke `completeReportedRun`, release a slot, or settle the task. A conversation has an owner-bound lifetime instead of the delegated task timeout, but each `executor.run` observation call remains finite. A new `running` result is valid only for the conversation arm and carries the exact persisted task, attempt, run and native identity; the host rechecks those facts and then calls the read-only resume arm for another bounded observation. No second claim or start grant is issued. A single call returns within a short poll budget, freeing the registry's eight-slot admission lane so `executor.stop` and other calls can proceed while sessions are idle. The ordinary `executor.run` arms and all other scoped capabilities retain their existing finite deadlines. On process loss, the host resumes only the same run and native ID; a missing exit receipt remains uncertain. User stop keeps `stopPending` until the exact interactive stop grant records and verifies wrapper exit. The host retains the current conversation activity and transcript behavior, and the public attach/answer path continues to use the persisted run-directory session socket.

The cutover tests must cover fresh and resumed Codex, Claude and OpenCode identities; attachment and permission-policy preservation; repeated turn reports without settlement; live attach, answer and stop; owner/provider/identity/attachment drift; a lost OpenCode identity-create reply; lost start/stop replies; restart while idle or awaiting input; provider disablement with zero built-in process effects; and a recorded exit versus an absent exit receipt. CT-11 needs an actual disposable conversation spanning at least two turns on the exact reviewed source. This route does not close takeover or configured remote full/PTY orchestration.

First-checkpoint tests cover: positive local interactive claim/start/report/attach/answer/stop; pipe grant cannot request interactive mode; unissued, replayed, wrong task/attempt/provider and disabled-provider calls have no process effect; lost start or report-completion receipt cannot start a second wrapper; owner swap, stop-before-start and restart retain the exact run; a `needs-input` report remains attachable without terminal settlement; recorded exit without report is failed, while death without recorded exit remains uncertain; reported success requires the host's exact reaped completion receipt. CT-11 exercises a real disposable interactive task through `bun run live` and the public attach/answer/stop route. The final SP09 review must also cover conversation, takeover and remote full/PTY route evidence; this first checkpoint alone cannot close SP09.

## Cutover and validation

Backend selection preserves `PACER_BACKEND`, account, conversation, managed child and Orca rules. Once the direct provider serves a route, its refusal yields `plugin_unavailable` or a recoverable pending state, without built-in direct fallback. The task runner applies complete provider outcomes through its existing settlement path. The production stop path has no direct kill or SSH fallback for provider-owned runs.

Tests cover disabled/foreign/replayed provider calls; policy, task, worktree, executable and directory drift; lost launch/stop receipts; state uncertainty; concurrent stop and start; restart with pending stop; full local delegate, attach, stop and retry; and remote configured-host denial and delivery. CT-11 runs a real local executor and the separately approved disposable BatchMode SSH route. Independent architecture, security, QA and repository review cover the final source. Unexercised behavior remains UNVERIFIED and the draft stays unready.
