# API and protocol compatibility rules

Applies to: `src/api/**`, `src/serve/**`, `src/mcp/**`, `docs/protocol.md`, `docs/protocol-v2.md` and `scripts/protocol-doc.ts`. Also applies to any client that reads API results or events.
Out of scope: CLI human-readable output formatting. Where `--json` output exists, it is in scope.
Owner: @lamtuanvu
Canonical sources: [docs/protocol.md](../../docs/protocol.md), [docs/protocol-v2.md](../../docs/protocol-v2.md), `src/api/protocol.ts`, [CHANGELOG.md](../../CHANGELOG.md)

| ID | Rule or convention | Status | Rationale/source | Verification |
|----|--------------------|--------|------------------|--------------|
| API-1 | Adding a field does not bump the protocol version. Clients must ignore unknown fields. | Established | docs/protocol.md | Review client parsing |
| API-2 | Removing or renaming a field, op or event needs a major protocol bump (`src/api/protocol.ts`). The previous major is served through a compat adapter for one pacer minor release. | Established | docs/protocol.md; 3.0 + `src/api/v2-compat` | Review; compat tests |
| API-3 | The protocol docs are generated by `bun run protocol:doc` and committed. A stale doc fails the tests. | Established | `test/api-protocol-doc.test.ts` | `bun run test` |
| API-4 | Errors are `CoreError(code, message, hint?, data?)`, mapped to HTTP status and JSON-RPC codes as documented. New codes are added to the protocol doc. | Established | `src/core/errors.ts`; docs/protocol.md Errors | Review; tests |
| API-5 | No operation runs free-form text in a shell. An executor may delegate child work only through a service-issued task/attempt grant constrained to its own work subtree; executor sessions without a valid grant are refused. Amendment 0.24.0 below names the assistant grant as a further, separate credential, and amendment 0.25.0 the workflow run grant. | Proposed amendment 0.14.0 for the scoped exception, 0.24.0 for the assistant grant; prior blanket refusal established until maintainer merge | docs/protocol.md; constitution 0.14.0 | Review; grant and transport tests |
| API-6 | Breaking protocol changes and compat-window removals are listed in CHANGELOG under the release that ships them. | Established | CHANGELOG (Keep a Changelog) | Review CHANGELOG diff |

### Run grant credential (amendment 0.25.0)

Approved by the maintainer on 2026-11-20 in the workflow frame design discussion; adopted when the maintainer merges this amendment PR (constitution "Amendment and exception policy", with an entry in [decisions.md](../decisions.md)).

| ID | Rule or convention | Status | Rationale/source | Verification |
|----|--------------------|--------|------------------|--------------|
| API-5b | The workflow orchestrator's run grant is a **distinct credential**. It is a `prg_` bearer (`prg_` + 64 lowercase hex) bound to exactly one root run id and one orchestrator turn (turn id and the turn's deadline), stored SHA-256-hashed at rest in the same grant store under its own `kind`. It is issued when the turn starts, expires at the turn's deadline, and is revoked when the turn settles or the run ends or is stopped. It authorizes only review, send-back, retry, stop, skip, escalate, sub-workflow submission, workflow choice, step results, step artifacts, answers to `auto` questions, and (from Phase 5) `run.sync_base` and `run.publish`, and only on tasks, steps and questions of its own run; `run.publish` also checks its own publishing gate, so the grant alone never publishes. `authorizeWorkOperation` answers for it first and refuses every other operation, so an unknown, expired or revoked `prg_` fails closed (403 at the HTTP gate; `not_allowed` from the core). It is never treated as the operator or an executor session, never delegates, and neither `pwg_` nor `pag_` answers for it or it for them. | Approved 2026-11-20 as amendment 0.25.0; adopted on maintainer merge | [workflow frame design](../../docs/specs/2026-11-19-workflow-frame-design.md) "Grant"; [ADR 0029](../../docs/decisions/0029-workflow-frame.md) "Rule amendment API-5b" | Phase 2 tests: `test/workflow-run-grant.test.ts` and the HTTP gate tests |

### Assistant grant credential (amendment 0.24.0)

Proposed; adopted only by the maintainer merging this amendment PR (constitution
"Amendment and exception policy": a `docs:` change to this rule file, with an entry
in [decisions.md](../decisions.md)).

| ID | Rule or convention | Status | Rationale/source | Verification |
|----|--------------------|--------|------------------|--------------|
| API-5a | The assistant grant is a **distinct credential**, not a task/attempt grant used as is and not an unrecognized one that would pass both gates. It is a `pag_` bearer (`pag_` + 64 lowercase hex, the shape of `pwg_`) bound to exactly one assistant turn — turn id, conversation id and the turn's deadline — stored SHA-256-hashed at rest in the same grant store under its own `kind`. It authorizes one operation only: `assistant.tool`, for that turn's `turnId`, while the grant is live. Both HTTP credential gates accept it only on `POST /v3/ops/assistant.tool` and map it to an **assistant-turn identity**: not the operator, not an executor session, no `PACER_ROLE`. `authorizeWorkOperation` answers for it first and refuses every other operation, so an unknown, expired or revoked `pag_` fails closed (403 at the HTTP gate; `not_allowed` from the core) and is never treated as the caller's own permissions. The grant is revoked when the turn ends, is cancelled or reaches its deadline. It never widens the executor refusals in `src/api/ops.ts` and `src/api/caller-policy.ts`, never delegates, never reaches a shell, and the two prefixes never answer for each other: a `pwg_` cannot call `assistant.*`, and a `pag_` cannot call anything else. | Proposed 0.24.0; adopted only by maintainer merge | [assistant backends design](../../docs/specs/2026-11-17-assistant-backends-design.md) §2 "The host runs every tool" and §3 "The per-turn grant"; constitution amendment 0.14.0 (API-5); open decision 5 of the same spec | `test/assistant-grant.test.ts`; `test/serve-http-assistant.test.ts`; `crates/server/src/serve/auth.rs` tests; `test/mcp-assistant.test.ts` |
